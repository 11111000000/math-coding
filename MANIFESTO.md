# Восемь принципов math-coding

## Введение

math-coding — это соглашение для записи архитектурных решений в форме проверяемых пакетов. Соглашение применяется к самому себе: ядро $S$, реализующее восемь принципов, само описывается через те же принципы. Это составляет неподвижную точку $Y$ в программистском смысле: фиксированная точка функции, преобразующей произвольное соглашение о решениях в соглашение, способное описывать себя.

Слоган соглашения — «Практика записывать решения перед кодом». Восемь принципов ниже формализуют то, что означает эта практика. Каждый принцип представляет собой минимальное утверждение, без которого соглашение либо теряет проверяемость, либо сводится к церемонии. Принципы сформулированы как теоремы и пакеты; их верифицирует одно статическое ядро на OCaml.

Соглашение хранит только текст и git-историю. Серверов, баз данных и фреймворков не используется. Каждое решение существует как каталог `math/<имя>/packet.md` с утверждением (proposition), фиксацией (witness — SHA коммита) и восемью полями frontmatter. Пять оснований и три расширения составляют восемь пакетов, проверяемых одним и тем же ядром; специального пути для самих оснований не существует.

## 1. Решение есть тройка

**Тезис.** Решение в math-coding структурно изоморфно тройке (proposition, code, witness), и соответствие её элементов проверяется ядром $S$.

**Обоснование.** Изоморфизм Карри-Ховарда утверждает, что proposition есть тип, code есть терм, inhabitation есть доказательство. В программной инженерии proposition становится утверждением о решении, code — его реализацией, witness — привязкой утверждения к коммиту, делающей inhabitation проверяемой. Без тройственной структуры proposition остаётся документацией без следствий: её изменение невозможно отследить. С тройкой proposition и code становятся проверяемой парой, а любое изменение кода требует либо обновления proposition, либо явного замещения.

**Формальное утверждение.**

$$\mathrm{Decision} = \langle \mathrm{name},\ \mathrm{proposition},\ \mathrm{code},\ \mathrm{witness},\ \mathrm{register},\ \mathrm{state},\ \mathrm{actor},\ \mathrm{confidence},\ \mathrm{superseded\_by} \rangle$$

```ocaml
type decision = {
  name          : string;
  proposition   : string;             (* непусто *)
  code          : string option;      (* опционально *)
  witness       : Sha.t option;       (* опционально *)
  register      : register;           (* fact | hypothesis | judgment | unknown *)
  state         : fsm_state;          (* draft | applied | reviewed | retired | abandoned *)
  actor         : actor;              (* human | agent | system *)
  confidence    : float;              (* [0, 1] *)
  superseded_by : string option;
  beneficiary   : beneficiary;
}
```

Ядро $S$ отвергает пакет с пустым `proposition`, требует `witness` для перехода в `applied` или `reviewed`, и сигнализирует расхождение при изменении proposition после фиксации.

**Перекрёстная ссылка.** Принцип `curry-howard.triple` фиксируется в `math/foundations/curry-howard/`. Все остальные основания и расширения наследуют структуру тройки: `temporal.lifecycle` вычисляет состояние по witness и git-истории, `constructive.proof` конкретизирует witness как воспроизводимую команду, `categorical.supersession-spo` определяет правила эволюции тройки через замещение.

**Работающий пример.** Принимается решение о политике TTL для кэша: proposition — «TTL = 60 секунд с ручной инвалидацией через `/admin/manual-invalidate`». Каталог `math/ttl-policy/packet.md` создаётся с этой proposition до того, как пишется код кэша. После реализации команда `mathc amend ttl-policy` фиксирует witness на текущий коммит. Команда `mathc check` сообщает `applied ✓`. Любое последующее изменение кода кэша без `mathc supersede` порождает расхождение, обнаруживаемое ядром.

## 2. Жизненный цикл вычисляется

**Тезис.** Жизненный цикл решения $L$ есть функция от решения и git-истории; $L$ вычисляется, а не хранится.

**Обоснование.** Решения эволюционируют. Утверждение, истинное в коммите $A$, может оказаться ложным в коммите $B$. Хранение состояния в виде перечисления допускает расхождение между заявленным и фактическим состоянием: разработчик изменяет код, но забывает обновить поле `status`. Вычисление состояния из истории git делает обнаружение расхождения автоматическим и фальсифицируемым — попытка лгать о состоянии становится невозможной, поскольку состояние есть следствие истории, а не её редактируемое поле.

**Формальное утверждение.**

$$L : \mathrm{Decision} \times \mathrm{Repo} \to \{\mathrm{Draft},\ \mathrm{Applied},\ \mathrm{Drift},\ \mathrm{Stale}\}$$

```ocaml
let lifecycle d repo =
  match d.witness with
  | None -> Draft
  | Some sha ->
    let prop_now = proposition_at d.name repo in
    if prop_now <> d.proposition then Drift
    else Applied
```

Только терминальные состояния (`reviewed`, `retired`, `abandoned`) требуют явного CLI-действия, поскольку кодируют человеческое суждение, а не механический факт.

**Перекрёстная ссылка.** Принцип `temporal.lifecycle` фиксируется в `math/foundations/temporal/`. Сочетается с `curry-howard.triple`: witness из тройки становится аргументом $L$. Связь с `process-fsm.fsm` (принцип 6) — переходы между состояниями автомата определяются историей, а не полем в файле.

**Работающий пример.** Разработчик изменяет файл `lib/cache.ex` уже после фиксации решения `ttl-policy`. Команда `mathc check` сообщает `ttl-policy: drift ?`, поскольку proposition и реализация разошлись. Разработчик либо откатывает код (`git revert` и `mathc amend`), либо фиксирует новую proposition через `mathc supersede ttl-policy ttl-policy-v2 "TTL = 30 секунд с инвалидацией по событию"`. В обоих случаях история согласована.

## 3. Доказательство воспроизводимо

**Тезис.** Состояние `proven` требует воспроизводимого свидетельства: повторный запуск команды должен давать записанный код выхода.

**Обоснование.** Классическая логика разрешает «доказано» без конструкции. Конструктивная логика требует терма — программы, нормализующейся к искомому значению. В программной инженерии терм — это перезапускаемая команда: тест, бенчмарк, проверка типа. Если результат не воспроизводится, утверждение не доказано — оно остаётся гипотезой. Это единственный эпистемический регистр, запускающий реальные действия ядра; остальные (`fact`, `hypothesis`, `judgment`, `unknown`) являются декларациями stance и не влияют на вердикты.

**Формальное утверждение.**

$$\mathrm{Reproducible} \triangleq \mathrm{Re\!-\!run}(\mathrm{command}) = \mathrm{recorded\_exit}$$

```ocaml
type evidence = {
  command       : string;
  recorded_exit : int;
  when_         : Sha.t;
}

let verify_evidence ev =
  if run_command ev.command = ev.recorded_exit
  then Pass
  else Fail
```

Пакет с `substrate: shell` или `substrate: pbt` имеет evidence — путь к команде и ожидаемый код выхода. При каждом `mathc check` ядро перезапускает команду и сравнивает результат. При несовпадении ядро сигнализирует расхождение.

**Перекрёстная ссылка.** Принцип `constructive.proof` фиксируется в `math/foundations/constructive/`. Связь с `curry-howard.triple` — воспроизведение команды есть нормализация в смысле Карри-Ховарда: программа `command` редуцируется к значению (коду выхода). Связь с `temporal.lifecycle` — поле `evidence.when_` есть git-SHA, синхронизирующий утверждение с историей.

**Работающий пример.** Решение `build-reproducibility` объявляет, что `cargo build --release` воспроизводим в идентичном окружении. Proposition фиксирует записанный код выхода `0`. Через полгода версия компилятора изменяется, и `cargo build --release` возвращает `1`. Команда `mathc check` сообщает `build-reproducibility: drift ?` — воспроизведение более не даёт записанного кода. Разработчик либо обновляет proposition через замещение, либо восстанавливает идентичное окружение.

## 4. Замещение — строгий частичный порядок

**Тезис.** Отношение «supersedes» на решениях есть строгий частичный порядок: иррефлексивный, асимметричный, транзитивный.

**Обоснование.** Решения эволюционируют. Когда proposition изменяется, прежнее решение не редактируется — оно замещается новым. Отношение замещения должно быть строгим частичным порядком, чтобы сохранить смысл. Иррефлексивность запрещает тривиальное самозамещение. Асимметрия исключает циклы. Транзитивность позволяет составлять цепочки в родословные. Без этих свойств история решений становится несогласованной: рецензент не способен определить, какое решение актуально.

**Формальное утверждение.** Пусть $\preceq$ обозначает «$a$ supersedes $b$». Тогда:

$$\forall a.\ \neg(a \preceq a) \quad\text{(иррефлексивность)}$$

$$\forall a, b.\ (a \preceq b) \Rightarrow \neg(b \preceq a) \quad\text{(асимметрия)}$$

$$\forall a, b, c.\ (a \preceq b) \wedge (b \preceq c) \Rightarrow (a \preceq c) \quad\text{(транзитивность)}$$

```ocaml
let check_spo decisions =
  List.for_all decisions ~f:(fun d ->
    not (supersedes d d) &&
    List.for_all (supersedees d) ~f:(fun other ->
      not (supersedes other d)) &&
    transitive_holds d)
```

**Перекрёстная ссылка.** Принцип `categorical.supersession-spo` фиксируется в `math/foundations/categorical/`. Соединяется с `temporal.lifecycle`: жизненный цикл вычисляется для каждого решения, а замещение связывает решения в историю того, что заменило что. Соединяется с `curry-howard.triple` через поле `superseded_by` в типе `decision`.

**Работающий пример.** Решение `error-handling` (Result + context, сентябрь 2025) замещается решением `error-handling-v2` (Result + tracing, март 2026). Затем `error-handling-v2` замещается `error-handling-v3`. Цепочка `error-handling` → `error-handling-v2` → `error-handling-v3` транзитивна: третье решение замещает первое по определению SPO. Ядро отвергает попытку создать цикл или самозамещение.

## 5. Регистр и обоснование

**Тезис.** Каждый пакет декларирует эпистемический регистр (`fact`/`hypothesis`/`judgment`/`unknown`) и численную уверенность; соглашение без мотивации есть церемония.

**Обоснование.** Решения принимаются с разной степенью уверенности. Факт требует воспроизведения; гипотеза — формулировки, открытой для опровержения; суждение — эксплицитного указания на возможный вред (обратимость, смягчение); неизвестное — честного признания границы. Без явного регистра эпистемическая честность превращается в самообман: разработчик заполняет поле «fact» без свидетельства, агент заполняет «fact» без проверки. Без обоснования proposition превращается в лозунг, не подлежащий критике.

**Формальное утверждение.**

$$\mathrm{register} \in \{\mathrm{fact},\ \mathrm{hypothesis},\ \mathrm{judgment},\ \mathrm{unknown}\}$$

$$\mathrm{confidence} : \mathrm{Decision} \to [0, 1]$$

Связь регистра и уверенности:

$$\mathrm{fact} \Rightarrow \mathrm{confidence} \in [0.95, 1]$$
$$\mathrm{hypothesis} \Rightarrow \mathrm{confidence} \in (0.5, 0.95)$$
$$\mathrm{judgment} \Rightarrow \mathrm{confidence} \in \{0, 1\} \text{ (категорично)}$$
$$\mathrm{unknown} \Rightarrow \mathrm{confidence} = 0$$

```ocaml
type register = Fact | Hypothesis | Judgment | Unknown

let validate_register r c =
  match r with
  | Fact       -> c >= 0.95
  | Hypothesis -> c > 0.5 && c < 0.95
  | Judgment   -> c = 0.0 || c = 1.0
  | Unknown    -> c = 0.0
```

Регистр `judgment` обязывает содержательное поле `motivation` (в секции `## Why`): указание на возможный вред (обратимость, смягчение, ответственность). Пустое `## Why` для `judgment` отвергается ядром с пометкой `Warn`.

**Перекрёстная ссылка.** Принцип `motivation.register-and-why` относится к расширениям и фиксируется в `math/extensions/motivation/`. Соединяется с `curry-howard.triple` через поле `register` в типе `decision`, и с `dialectic-tas.required-sections` (принцип 7) — для регистра `judgment` требуется структура тезис/антитезис/синтез как конкретизация мотивации.

**Работающий пример.** Агент принимает решение «отключить проверку подписи пакетов на CI для ускорения сборки». Регистр — `judgment`, поскольку это решение о доверии. Confidence = 0 (категорично: либо отключаем, либо нет). Мотивация содержит указание на обратимость (флаг CI), на возможный вред (подделка пакетов), на смягчение (ограничение только на ветку `feature/*`). Proposition не принимается без заполненной мотивации; ядро возвращает предупреждение с указанием на пустое поле.

## 6. Автомат состояний с одним запретом

**Тезис.** Решения существуют в пяти состояниях — `draft`, `applied`, `reviewed`, `retired`, `abandoned`; единственный запрещённый переход — `draft` → `reviewed` без `witness`.

**Обоснование.** Без явного автомата состояний пакет остаётся «применённым» по умолчанию, и рецензия теряет смысл. С пятисостоявным автоматом каждое решение проходит явный путь: от proposition (draft) к inhabitation (applied) к человеческой проверке (reviewed), с возможностью выхода через `retired` или `abandoned`. Запрет перехода `draft` → `reviewed` без `witness` закрывает тривиальный обходной путь: нельзя объявить решение проверенным, не пройдя inhabitation через git-фиксацию. Это минимальное и достаточное ограничение: одно правило закрывает все обходы.

**Формальное утверждение.** Состояния и допустимые переходы:

| from | to | условие |
|---|---|---|
| `draft` | `applied` | требуется `mathc amend` (установка `witness`) |
| `applied` | `reviewed` | требуется подпись рецензента (`mathc review`) |
| `applied` | `draft` | требуется `mathc supersede` или явный откат |
| `applied` | `retired` | CLI: `mathc retire <name>` |
| `applied` | `abandoned` | CLI: `mathc abandon <name>` |
| **`draft`** | **`reviewed`** | **запрещено** — невозможно без `witness` |

```ocaml
let transition d target =
  match d.state, target with
  | Draft, Reviewed ->
    Error "draft→reviewed без witness запрещён"
  | Draft, Applied when d.witness = None ->
    Error "applied требует witness"
  | _, _ -> Ok target
```

**Перекрёстная ссылка.** Принцип `process-fsm.fsm` относится к расширениям и фиксируется в `math/extensions/process-fsm/`. Соединяется с `curry-howard.triple` (без witness пакет не inhabits), с `temporal.lifecycle` (состояние автомата есть подмножество жизненного цикла), с `actor-discipline.signed-commits` (переход в `reviewed` требует подписи в режимах `Strict` и `Lenient`).

**Работающий пример.** Решение `auth-skip-csrf` (отключить CSRF-проверку для API-эндпоинтов) создаётся в состоянии `draft`. Разработчик пытается сразу вызвать `mathc review auth-skip-csrf` без `amend`. Ядро отвергает: переход `draft → reviewed` запрещён. Разработчик вынужден сначала зафиксировать witness через `mathc amend`, и лишь затем — после подписи рецензента — перейти в `reviewed`.

## 7. Тезис, антитезис, синтез обязательны

**Тезис.** Пакеты с эпистемическим регистром `judgment` требуют разделов `## Thesis`, `## Antithesis`, `## Synthesis`; структурная форма диалектики обязательна для человеческих суждений.

**Обоснование.** Человеческое суждение без явного рассмотрения контр-аргументов склонно к самообману. Диалектическая традиция показывает, что синтез достижим только через прохождение тезиса и антитезиса; сокращение этой структуры превращает суждение в декларацию. В программной инженерии суждение о доверии, безопасности или обратимости должно содержать явный антитезис — наиболее сильный контраргумент против принятого решения. Без него proposition становится лозунгом, и рецензент не может отличить продуманное решение от импульсивного.

**Формальное утверждение.** Пакет с `register = judgment` (или `actor = human`) обязан содержать разделы:

```markdown
## Thesis
<формулировка утверждения с обоснованием>

## Antithesis
<наиболее сильный контраргумент и его разбор>

## Synthesis
<итоговое решение с указанием на обратимость и смягчение>
```

```ocaml
let validate_dialectic d =
  if d.register = Judgment || d.actor = Human then
    let body = read_packet_body d in
    if has_section "Thesis" body
       && has_section "Antithesis" body
       && has_section "Synthesis" body
    then Pass
    else Warn "Judgment требует разделов Thesis/Antithesis/Synthesis"
  else Pass
```

Отсутствие любого из трёх разделов выдаёт `Warn` (не `Fail`); однако convention настоятельно рекомендует заполнить все три.

**Перекрёстная ссылка.** Принцип `dialectic-tas.required-sections` относится к расширениям и фиксируется в `math/extensions/dialectic-tas/`. Соединяется с `motivation.register-and-why` (принцип 5) — мотивация для `Judgment` конкретизируется через структуру TAS, и с `curry-howard.triple` — тезис есть proposition, антитезис есть контр-evidence, синтез есть inhabitation с учётом контраргумента.

**Работающий пример.** Решение `vendor-lock-in` (использование проприетарного SaaS для логирования) принимается в три часа ночи как аварийное. Регистр — `Judgment`. Разработчик пишет `## Thesis` (SaaS быстрее развернуть), `## Antithesis` (vendor lock-in делает миграцию дорогой; при падении вендора логи теряются), `## Synthesis` (принимаем SaaS, но с абстракцией интерфейса и квартальной ревизией зависимости). Без раздела `Antithesis` ядро выдаёт предупреждение — это вынуждает разработчика рассмотреть контр-аргумент даже в спешке.

## 8. Подписи фиксируют автора

**Тезис.** Решение фиксирует автора через подписи коммитов; режим подписи (`strict`/`lenient`/`off`) определяется проектом и проверяется ядром.

**Обоснование.** Решение без автора не имеет ответственности. В распределённой разработке (человек, агент, агентурная система) подпись коммита — единственный криптографически проверяемый способ связать proposition с субъектом. Без явного режима подписи проект оказывается в ситуации «все подписаны, но никто не проверяет» — или, наоборот, «никто не подписан, и авторство неотслеживаемо». Три режима — `strict`, `lenient`, `off` — покрывают три класса проектов: критическая инфраструктура, обычная разработка, прототипирование.

**Формальное утверждение.**

$$\mathrm{SigningMode} = \{\mathrm{Strict},\ \mathrm{Lenient},\ \mathrm{Off}\}$$

| режим | требование | следствие |
|---|---|---|
| `Strict` | каждый коммит пакета имеет валидную GPG/SSH подпись | ядро отвергает пакет без подписи (`Fail`) |
| `Lenient` | коммит `amend` имеет подпись; остальные — нет | ядро отвергает пакет, если `amend`-коммит без подписи (`Warn`) |
| `Off` | подписи не требуются | ядро не проверяет подписи |

```ocaml
type signing_mode = Strict | Lenient | Off

let verify_signing d mode =
  match mode with
  | Strict -> all_commits_signed d
  | Lenient -> List.for_all (amend_commits d) ~f:signed_p
  | Off -> Ok
```

Поле `signed_by` в типе `decision` фиксирует отпечаток ключа (fingerprint) автора `amend`-коммита. Поле присутствует в пакете начиная с состояния `applied`.

**Перекрёстная ссылка.** Принцип `actor-discipline.signed-commits` относится к расширениям и фиксируется в `math/extensions/actor-discipline/`. Соединяется с `curry-howard.triple` через поле `signed_by`, с `process-fsm.fsm` (принцип 6) — переход в `reviewed` требует подписи в режимах `Strict` и `Lenient`, с `temporal.lifecycle` (принцип 2) — авторство восстанавливается по witness-коммиту.

**Работающий пример.** Проект `core-infrastructure` устанавливает режим `Strict`. Решение `crypto-policy` создаётся человеком, но коммит `amend` создаётся агентом без настроенного GPG-ключа. Ядро `mathc check` сообщает `crypto-policy: ✗ no signature`. Агент настраивает ключ, разработчик пересоздаёт коммит. В прототипе `personal-scratchpad` режим `Off` — ядро не проверяет подписи, и тот же сценарий проходит без сопротивления.

## Соглашение применяется к себе (kernel-uniformity)

math-coding обладает свойством kernel-uniformity: ядро $S$, верифицирующее пакеты, само описывается через те же восемь принципов. Это и есть неподвижная точка $Y$ в программистском смысле:

$$Y(\mathrm{math\text{-}coding}) = \mathrm{math\text{-}coding}$$

$Y$ есть функция, превращающая произвольное соглашение о решениях в соглашение, способное описывать себя. math-coding — фиксированная точка этой функции.

Пять оснований (`curry-howard`, `temporal`, `constructive`, `categorical`, `motivation`) и три расширения (`process-fsm`, `dialectic-tas`, `actor-discipline`) являются обычными пакетами в каталогах `math/foundations/` и `math/extensions/`. Они не образуют «метауровень». Их структура — та же: proposition в frontmatter, witness в git-истории, состояние, вычисляемое ядром. Когда ядро проверяет пакет `curry-howard`, оно запускает тот же код, что и для пользовательского пакета. Специального пути не существует; это и есть формальное выражение $Y$-свойства.

Каждое основание и расширение ссылается на другие через теоремы: `curry-howard.triple` предоставляет базовую тройку; `temporal.lifecycle` строит поверх неё; `constructive.proof` конкретизирует witness как воспроизводимую команду; `categorical.supersession-spo` определяет эволюцию; `motivation.register-and-why` добавляет эпистемическую честность; `process-fsm.fsm` конкретизирует жизненный цикл; `dialectic-tas.required-sections` конкретизирует мотивацию; `actor-discipline.signed-commits` фиксирует авторство. Все восемь — взаимно нагруженные.

Если какое-либо из утверждений в foundation-пакетах окажется ложным, ядро обнаружит расхождение тем же способом, что и для пользовательского пакета: через `Drift` или через структурную ошибку. Это означает, что math-coding способен к самоисправлению: ошибка в описании принципа обнаруживается и устраняется через `supersede`. Соглашение не имеет непроверяемых исключений.

## Заключение

math-coding существует потому, что proposition не есть код, а код не объясняет себя. Без явного proposition код становится неизменяемым — каждое изменение рискует разрушить намерение, которое никто не зафиксировал. С proposition намерение становится проверяемым: proposition и code становятся парой, расхождение которой обнаруживается автоматически.

Восемь принципов минимальны и взаимно нагружены. Каждый из них несёт нагрузку: удаление `curry-howard.triple` лишает proposition кода; удаление `temporal.lifecycle` делает дрейф необнаружимым; удаление `constructive.proof` превращает доказательство в декларацию; удаление `categorical.supersession-spo` допускает циклы в истории решений; удаление `motivation.register-and-why` лишает эпистемической честности; удаление `process-fsm.fsm` устраняет рецензию; удаление `dialectic-tas.required-sections` устраняет обязательство рассматривать контр-аргумент; удаление `actor-discipline.signed-commits` устраняет авторство. Ни один из восьми нельзя убрать без потери смысла соглашения.

Соглашение запускаемо: один статический бинарь на OCaml верифицирует структуру, жизненный цикл, свидетельство и замещение. Соглашение текстовое: только plain text и git. Соглашение минимальное: ~700 строк OCaml, один бинарь, восемь пакетов. Соглашение применимо к себе: $Y(\mathrm{math\text{-}coding}) = \mathrm{math\text{-}coding}$.

# Полевой пилот Math Coding v5

## Статус

Это зарегистрированный протокол и стартовая инвентаризация, не отчёт об
эффективности. Реальных задач в `field-tasks.jsonl` пока нет. `dry-run.jsonl`
содержит только синтетические записи для проверки формата и не входит в
результаты пилота.

### Дисциплина версий

Установленный и свежесобранный `mathc` могут иметь разные fingerprints. Это
корректно инвалидирует evidence, но может испортить сравнение. Перед каждым
сравнением записываются `mathc --version`, model и начальная ревизия. Внутри
одного `comparison_id` validator отклоняет смену model или `mathc_build`, а
внутри одной задачи — смену исходной ревизии.

## Что измеряется

Основная единица — одна задача с независимым решением о принятии и последующим
наблюдением. Число claims, `holds` и evidence-записей не является метрикой
эффективности.

Основные показатели:

- принятие по исходному человеческому критерию;
- дефекты после принятия и возвраты на доработку;
- время handoff до первого осмысленного действия следующего исполнителя;
- полное время и стоимость до принятого результата;
- повторные исследования, вызовы `mathc`, ошибки controls и environment mismatches;
- ложные `Green`, `Green` с `uncovered`, ослабления claims после `fail`.

Причины трения записываются отдельными классами: ошибка реализации, слабый claim,
слабый verifier, неправильный control, изменение источника, среда, инфраструктура,
uncovered, handoff, onboarding. Они не складываются в один счётчик «поймано
ошибок».

## Порядок работы

1. Зафиксировать задачу, arm, модель, build-id, начальную ревизию и критерий
   принятия до начала работы.
2. Включать первые пять подходящих задач в каждом подтверждённом v5-проекте без
   отбора по результату. Записывать также незавершённые и инфраструктурные исходы.
3. Заполнять одну JSON-запись на прогон в `field-tasks.jsonl`; образец —
   `dry-run.jsonl`.
4. Для полевых задач observation window — семь календарных дней после принятия.
   Ранний дефект или возврат записывается сразу; `observation_complete` становится
   `true` только после завершения окна.
5. Не записывать prompts, код, команды, stdout, секреты или личное содержимое.
   `accepted_by` — идентификатор ревьюера, не само решение инструмента.
6. После полевого пилота выбрать шесть реальных задач для контролируемого
   сравнения: по две из каждого подтверждённого проекта, три руки на задачу.
7. Не запускать `mathc-stand` в живых деревьях: он исполняет команды проекта и
   пишет evidence. Для измерений использовать отдельные worktree.

Проверка формата и сводка:

```sh
python3 docs/measurements/task-ledger.py validate docs/measurements/field-tasks.jsonl
python3 docs/measurements/task-ledger.py summary docs/measurements/field-tasks.jsonl
```

## Инварианты ledger

- Все 33 поля обязательны; неизвестные и повторные поля отклоняются.
- `accepted` требует независимого `accepted_by`; другие исходы не могут его иметь.
- `handoff_seconds = null` означает, что handoff не измерялся.
- До завершения observation window дефекты и возврат могут быть `null`; ранние
  наблюдения записываются числом/boolean. При завершённом окне оба значения
  обязательны.
- `excluded` требует заранее объявленной причины; остальные исходы не могут иметь
  `exclusion_reason`.
- Один `run_id` встречается один раз; одна задача не может иметь две записи одной
  руки. Не все полевые задачи обязаны иметь три руки, но контролируемое сравнение
  проводится для всех трёх рук из одной ревизии.
- `summary` показывает все исходы, число завершённых наблюдений, дефекты, возвраты,
  медиану handoff и затраты. Он не вычисляет доказательство эффективности и не
  скрывает незавершённые наблюдения.

Validator и dry run являются проверкой измерительной схемы, а не доказательством
пользы Math Coding. Автоматическая telemetry и централизованные dashboard до
результатов первого ручного пилота не добавляются.

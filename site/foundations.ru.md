# Основания

> **От аксиом к OCaml.** Каждое основание — пакет
> под `decisions/`, который отображает аксиому в
> механизм ядра и обязательство верификации. Пять
> аксиом выровнены с пятью решениями bootstrap, через
> которые проходит шлюз репозитория начиная с
> v3.0.0.19:

![Пять аксиом слева, в паре с решениями bootstrap, которые они обеспечивают, справа: A0 Separation -> bootstrap-v3, A1 Feedback -> attestation-store-fill, A2 Invariants -> kernel-conformance-runner, A3 Self-application -> mathc-self-check-subcommand, A4 Care -> validate-and-context. Нижний колонтитул: "Каждая аксиома операционализируется конкретным решением, которое ядро проверяет; аксиомы не декларативны."](assets/axiom-graph.svg)

Каждая строка диаграммы выше соответствует одному из пяти
разделов ниже. Диаграмма — это спецификация; разделы ниже —
это реализация.

## A0 — Разделение → `bootstrap-v3`

**Аксиома.** Виды различны; цепочка идёт одним путём.
`намерение ≠ решение ≠ обязательство ≠ изменение ≠
аттестация ≠ наблюдение ≠ ревизия`.

**Механизм.** Закрытые варианты в `lib/domain.ml` для
каждого вида; префиксы на документ; закрытые поля
`additionalProperties` в JSON-схемах под `schemas/`.
Разборщик отвергает любой документ, чей идентификатор
не входит в закрытое множество, объявленное в
соответствующей схеме.

**Верификация.** Обязательство `packages-kernel-walker` в
`decisions/mathc-packages-subcommand.yaml` перечисляет
каждое решение в репозитории и выдаёт типизированный
JSON; обходчик падает на виде, не входящем в закрытое
множество.

Диаграмма A0 (показанная на графе аксиом выше) сама
является упражнением A0: каждая аксиома и каждое решение —
различный вид. Диаграмма — не блок-схема протокола;
это карта происхождения ограничений.

## A1 — Обратная связь → `attestation-store-fill`

**Аксиома.** У каждого обязательства есть путь к
наблюдению: `обязательство → предсказание → наблюдение →
ревизия`. Без наблюдения обязательство — пожелание.

**Механизм.** `attestations/*.json` записывает каждую
пару «решение — обязательство» как вердикт `pass | fail |
stale | unknown | missing | no_store`. `lib/attestations.ml`
загружает хранилище и сопоставляет каждую запись со
шлюзом ядра.

**Верификация.** `scripts/generate-attestations.py`
выпускает 94 файла аттестаций в каждом релизе;
`mathc gate BASE HEAD` сообщает зелёный статус для
`gate-pass.t` / `gate-fail.t` / `gate-stale.t` (cram-фикстуры
в `tests/cli/`).

Диаграмма жизненного цикла аттестации (отрисованная в
нижней части этой страницы) показывает пять стадий,
которые превращают CI-прогон в вердикт: production
захватывает fingerprint субстрата, store записывает
документ аттестации, join сопоставляет запись с её
обязательством, verdict собирает результаты по
обязательствам в единое заключение, а expiry переключает
обязательство в `Inconclusive`, когда достигнут его
`valid_until`. Аксиома A1 утверждает, что у каждого
обязательства есть такой путь; жизненный цикл и есть
этот путь.

## A2 — Инварианты и восстановление → `kernel-conformance-runner`

**Аксиома.** Для каждого инварианта `I` оператор
восстановления `R` авторизован. Решение конечно.

**Механизм.** `lib/gate.ml` оценивает каждое обязательство
по хранилищу аттестаций и выдаёт типизированные записи
`Gate.gap` с `causes` и `remedies`. Ядро никогда не
блокирует слияние, не назвав меру устранения.

**Верификация.** `tests/conformance.ml` перечисляет
каждую фикстуру и проверяет, что исполнитель не падает;
`mathc self-check` возвращает `pass` на чистом `main`
HEAD.

Решение `kernel-conformance-runner` привязывает A2 к
исполняемому файлу `tests/conformance.ml`. Каждая
фикстура в корпусе conformance парна с соответствующим
тип-кодом `mc-*` в `lib/diagnostic.ml::explain`. Если
исполнитель падает, сообщение о дефиците называет ту
запись реестра, которую исполнитель ожидал потребить, —
это типизированное указание на дефицит, а не трассировка стека.

## A3 — Само-применение → `mathc-self-check-subcommand`

**Аксиома.** Правила управляют своими изменениями:
`(K_n, P_n) → (K_{n+1}, P_{n+1})` требует Gate Open,
Conformance Pass, Migration round-trips, VerdictDiff в
пределах DeclaredSemanticChanges, SelfVerify Pass.

**Механизм.** `mathc self-check` обходит каждое решение в
`decisions/` и выдаёт JSON-вердикт, называющий ядро,
которое его произвело (SHA-256 бинарника), и дайджест
репозитория. Вердикт пропускается через шлюз по
**текущим** правилам, до того как блокировка
повышается.

![A3 Само-применение: пара (ядро, политика) сама является своим шлюзом. Два состояния (K_n, P_n) и (K_{n+1}, P_{n+1}) соединены переходом. Условия-охраны: Gate = Open, Conformance = Pass, Migration = Pass, VerdictDiff subset of DeclaredSemanticChanges, SelfVerify = Pass.](assets/a3-self-application-flow.svg)

Диаграмма выше — визуализация аксиомы A3. A3 говорит,
что ядро должно проверять собственный путь обновления:
правила, контролирующие `(K_n, P_n) → (K_{n+1}, P_{n+1})`,
те же самые, что контролируют любой другой переход.
Пять охран на диаграмме — это предусловия, которые ядро
обеспечивает для самого себя перед публикацией нового
релиза.

**Верификация.** `tests/cli/self-check-{pass,fail,unknown}.t`
зелёные; обязательство
`mathc-self-check-dispatcher-shipped` в
`decisions/mathc-self-check-subcommand.yaml` выполнено.

## A4 — Забота → `validate-and-context`

**Аксиома.** Для каждого обязательства: кому выгодно,
кто страдает, кто ответственен, когда будет
пересмотрено.

**Механизм.** `decision.risk.owner`, `obligation.decision`,
`assumption.owner`, `waiver.issuer`,
`attestation.producer_identity` — **обязательные** поля
в соответствующих схемах. Разборщик отвергает решение
без владельца.

**Верификация.** `fixtures/conformance/decision/negative-*.yaml`
отвергаются `Decision.parse_decision` за отсутствие
обязательных полей;
`fixtures/conformance/decision/positive-*.yaml` принимаются.

A4 — это аксиома, которая привязывает остальные четыре
к людям. A0, A1, A2 и A3 все структурны — они описывают,
как ядро перемещает байты. A4 говорит, что ядро
существует потому, что людям не всё равно, и что люди,
которым не всё равно, несут подотчётность. Решение
`validate-and-context` называет четыре обязательных поля
в схеме; без них ядро отказывает артефакту.

## Расширения

Три расширения добавляют поверхность ядра, не меняя
пять оснований:

| Расширение | Поверхность | Cram-фикстура |
|------------|-------------|----------------|
| `mathc-explain-subcommand` | `mathc explain decision:foo` → `{kind,id,digest,path,body}` | `explain-{positive,negative}.t` |
| `mathc-self-check-subcommand` | `mathc self-check` → JSON-вердикт | `self-check-{pass,fail,unknown}.t` |
| `mathc-packages-subcommand` | `mathc packages --format=text\|json\|html` → список пакетов | `packages.t` |

Ядро на v3.3.0 поставляет 3.2-идеал алгебру поверх них.
Раздел сайта [Packages](packages.html) — живой вердикт
каждого активного решения; текущая сборка сообщает о
93 активных решениях / 330 обязательствах (313 pass /
16 missing / 1 unknown).

## Сопутствующие диаграммы

Следующие рисунки — визуальный словарь, который
использует остальная часть сайта. Каждый рисунок
выполнен в одной и той же палитре Тufte, чтобы
публикуемая поверхность протокола выглядела единообразно
на разных страницах.

![Жизненный цикл аттестации: production, store, join, verdict, expiry. Пять стадий от CI-прогона до вердикта шлюза.](assets/attestation-lifecycle.svg)

Жизненный цикл аттестации — это конкретная форма A1:
у каждого обязательства есть путь к наблюдению, и этот
путь — production → store → join → verdict → expiry.
Пять стадий — это в точности пять строк решения
`attestation-store-fill`; диаграмма — то, как выглядит
решение в движении.

![Поток контрпримера: автор записывает набор контрпримеров в decision.yaml; ядро проверяет |C(D)| >= 1 для любого решения, чей режим не tiny; при отсутствии шлюз блокирует слияние и эмитит remediation. Контрпример — машино-проверяемая принуждающая функция; антитезис — связная контр-позиция, с которой автор взаимодействовал (algebra section 11, 11.1).](assets/counterexample-flow.svg)

Поток контрпримера — конкретная форма слота
`counterexample` в диалектическом методе. A1 говорит,
что у каждого обязательства должен быть путь к
наблюдению; слот контрпримера — это путь, который автор
предоставляет до того, как ядро публикует решение.

![Переход аксиомы: оракул re_evaluate(d, A_new) возвращает одно из трёх значений ReEvaluationStatus — Compatible, Inconclusive, StaleClaim — а вердикт шлюза — это max_verdict по impact-list (algebra section 17).](assets/axiom-transition.svg)

Поток перехода аксиом — конкретная форма обязательства
`re-evaluate-decisions`. A3 говорит, что правила
управляют собственными изменениями;
`re-evaluate(d, A_new)` — это механизм, которым ядро
проверяет изменение правил до его принятия.

![Динамика доверия: парадокс лжеца разрешается за один шаг — узел доверяет только собственному наблюдению и наблюдению следующего узла, никогда утверждению следующего узла; система корректна, потому что утверждение распространяется только через наблюдённые утверждения, а наблюдённое утверждение по определению честно.](assets/trust-dynamics.svg)

Диаграмма динамики доверия — лежащая в основе теория
графов для A1. Каждый узел доверяет только своему
наблюдению и наблюдению следующего узла; утверждения
распространяются только через наблюдённые утверждения.
A1 — это аксиома; диаграмма динамики доверия — граф,
который её удовлетворяет.

![Fingerprint субстрата: ядро сводит субстрат (хранилище решений, хранилище аттестаций, активная политика) в единый sha256, fingerprint. Два субстрата эквивалентны по A0 тогда и только тогда, когда совпадают их fingerprint'ы; ядро не будет рассматривать вопрос "это одно и то же?" никаким иным способом, кроме равенства fingerprint'ов.](assets/substrate-fingerprint.svg)

Диаграмма fingerprint субстрата — формальный
двойник A0. Виды различны; идентичность субстрата — это
fingerprint, который отличает его от любого другого
субстрата. Два субстрата эквивалентны по A0 тогда и
только тогда, когда совпадают их fingerprint'ы.

![Конечный автомат waiver: FSM waiver имеет четыре состояния — Active, Grace, Expired, Revoked — и три перехода. Waiver входит в Grace при достижении его valid_until; waiver входит в Expired, когда grace исчерпан; waiver входит в Revoked, когда выпускающий человек отзывает его. Решение, которое модифицирует waiver, удерживается в StaleClaim во время Grace и Expired, а ядро отказывается гейтить любой артефакт, зависящий от него в этих состояниях.](assets/waiver-state-machine.svg)

Конечный автомат waiver — конкретная форма решения
`waiver-infrastructure-2026-10`. Waiver — это
утверждение человека, что обязательство не применяется к
конкретному изменению; FSM записывает жизненный цикл
waiver'а, а ядро отказывается гейтить любой артефакт,
зависящий от waiver'а в не-Active состоянии.

![Конверт трения: риск (ось X) против строк изменённого кода (ось Y) для четырёх ступеней лестницы трения. Конверт silent — наименьший прямоугольник, block — наибольший. Mode — это потолок: mode изменения — это наименьший конверт, содержащий его позицию. Конверт мал для опечаток, велик для изменений схемы; ядро выбирает уровень трения, соответствующий конверту.](assets/friction-envelope-plot.svg)

График конверта трения — это геометрия функции `risk`.
Mode — наименьший конверт, содержащий позицию
`(risk, lines_changed)` изменения; уровень трения — это
ступень, чей конверт совпадает с mode изменения.
Исправление опечатки лежит внутри конверта silent;
изменение схемы лежит внутри конверта block.

![Радар качества: шесть осей для измерения качества изменения (correctness, scope, alignment, attestation, recovery, cost). Каждая ось от 0 до 1; ядро эмитит по одной оценке на ось при каждом прогоне шлюза. Изменение приемлемо, когда все шесть выше объявленного политикой пола; пол показан как шестиугольник. Радарный график накладывает пол поверх текущих оценок, чтобы ревьюер мог одним взглядом увидеть, какие оси ниже порога.](assets/quality-radar.svg)

Радар качества — визуализация обязательства
`change-quality`. Каждая ось — отдельная грань качества
изменения; пол задаётся политикой. Ревьюер, желающий
узнать, почему изменение было отклонено, может прочесть
радар и увидеть, какая ось упала ниже пола.

![Три независимые шкалы отчётности о времени: wall-clock-minutes (настенные минуты), token-budget (лимит токенов), step-count (число шагов). Эти три шкалы независимо наблюдаемы и не могут быть объединены в единую натурально-языковую оценку (AGENTS.md section Honest time reporting; algebra section 18).](assets/reasoning-budget.svg)

Диаграмма reasoning-budget обеспечивает правило
честной отчётности о времени в проекте. Три шкалы
(wall-clock минуты — настенные минуты; token budget —
лимит токенов; step count — число шагов) независимо
наблюдаемы; ядро сообщает все три и отказывается
объединять их в единую натурально-языковую оценку.
Рисунок показывает три шкалы как раздельные оси;
ревьюер, желающий узнать, сколько «времени» заняло
изменение, должен прочесть все три.

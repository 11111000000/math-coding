# Манифест

> **Восемь принципов, один статический исполняемый файл.**
> math-coding — дисциплина записи решений **до** кода;
> ядро проверяет, что эти записи соблюдаются.

## Что это и чем отличается

mathcoding — протокол обеспечения качества изменений
в программном обеспечении: каждое изменение привязывается
к записанному обязательству, ограниченному свидетельству
и детерминированному вердикту ядра (`pass`, `fail`,
`inconclusive`, ...). Это не CI, не «документ-как-код»
и не «LLM-судья»; ближайшие соседи — Spec-Driven Development
и ADR/MADR. Подробное сравнение с двадцатью методологиями —
на странице [Отличия](differences.html).

## Проблема

Решения забываются — но не потому, что их не пишут.
Пишут: `docs/adr/0007-cache-revocation.md`,
`specs/checkout-flow.md`, промпт-судья в CI. К третьему
релизу исходная причина уже не восстанавливается без
археолога. Код расходится с замыслом, потому что мы путаем
два разных действия — записать решение и проверить его.
Ни один из привычных инструментов их не различает.

Три ближайших подхода оставляют эту подмену без ответа:

- **ADR (Nygard / MADR).** Решение фиксируется в Markdown
  — но нет шлюза, который сверяет ADR с кодом. Запись
  устаревает молча; «Status: superseded» остаётся строкой,
  а не следом в DAG ревизий.
- **Spec-Driven Development** (GitHub Spec Kit, AWS Kiro,
  2025). Спецификация предшествует коду — но не привязана
  к верификатору. Спецификация без проходящего теста
  считается принятой; формальное соответствие выдаётся
  за верификацию.
- **LLM-как-судья.** Модель выносит вердикт — но без
  класса источника, без входов и без времени. «Проверено»
  и «не проверено» в её оценке неразличимы: вердикт
  модели — это `reviewed`, а не `observed`.

У всех троих одна и та же подмена: записанное выдаётся
за проверенное. mathcoding разводит их по разным видам
и связывает заново — через обязательство, аттестацию
и вердикт. Если аттестации нет, обязательство — `inconclusive`.
«Не проверял» не означает «проверил, и оно работает».

math-coding меняет порядок: каждое архитектурное
обязательство записывается **до** кода, а ядро сверяет
обязательство с кодом при каждом слиянии. Дисциплина
называется **mathcoding**.^[Минимальный элемент,
замыкающий петлю обратной связи в рабочей дисциплине, —
верификатор: программа, которую можно перезапустить
и чей код завершения означает «успех» или «провал».]

![архитектура math-coding: пять концентрических слоёв вокруг человека — аксиомы, ядро, объекты протокола, сайт и инструменты, проекты пользователей.](assets/architecture-overview.svg)

Приведённая выше диаграмма архитектуры — мысленная модель
этого манифеста. Человек находится в центре: каждое
изменение самого math-coding, ядра, объектов протокола,
сайта и инструментов, проектов пользователей проходит
через один и тот же math-coding. Протокол окружает
человека пятью концентрическими слоями; ничто не минует
шлюз.

## Чем это не является

- Не исполнитель непрерывной интеграции. Используйте
  `scripts/dev` или механизм GitHub Actions.
- Не генератор документации. Спецификация нормативна;
  инструменты читают спецификацию.
- Не инструмент рецензирования кода. Используйте агентов
  `paseo` или встроенное в GitHub рецензирование.
- Не наблюдатель среды исполнения. Ядро работает офлайн;
  аттестации производятся вне сборочного конвейера.

Работа ядра — **петля обеспечения качества**: у каждого
обязательства есть путь к наблюдению; каждое наблюдение
отнесено к известному классу источника; каждый класс
источника ограничен субъектом, входами и временем.

![Человек в петле: три роли (автор, рецензент, оператор) затрагивают пять точек протокола. Пятая (подписать аттестацию или выдать освобождение) — единственная, которую ядро не может заменить.](assets/human-in-the-loop.svg)

Приведённая выше диаграмма «человек в петле» — ответ
манифеста на вопрос «где в автоматизированном протоколе
место для человека?». Ответ: в трёх ролях и пяти точках.
Ядро — пол; человек — потолок.

## Принципы на v3.0

Ядро проверяет обязательства, заявленные в каждом
активном решении (52 активных решения / 207 обязательств
на чистом `main` HEAD по состоянию на последний билд),
все оформлены как пакеты в `decisions/`. Восемь из этих
пакетов образуют минимальный набор, замыкающий петлю
начальной загрузки:

| Группа | Принцип | Что утверждает |
|--------|---------|-----------------|
| основа | `bootstrap-v3` | ядро способно проверить этот репозиторий |
| основа | `kernel-conformance-runner` | каждая фикстура перечислена и выполнена |
| основа | `validate-and-context` | каждое решение разбирается и открывает капсулу |
| основа | `gate-decision` | вердикт шлюза проверяется сценарно |
| основа | `attestation-store-fill` | хранилище аттестаций заполнено |
| расширение | `mathc-explain-subcommand` | `mathc explain` разрешает ссылки вида `decision:` |
| расширение | `mathc-self-check-subcommand` | `mathc self-check` возвращает автоматический вердикт |
| расширение | `mathc-packages-subcommand` | `mathc packages` — поверхность первого класса |

Восемь — не произвольное число. Это минимум, замыкающий
петлю начальной загрузки: от первого коммита
(`v3-alpha-0.0.1`) до момента, когда ядро способно
проверить само себя (коммит `8fa7fcf`), каждое изменение
должно было получить одобрение всех восьми. Сейчас оба
выполнены. Полный живой реестр — на странице
[Packages](packages.html).

![Роли человека и виды объектов: какая роль выбирает какой из семи видов. Автор создаёт, рецензент рецензирует, оператор оперирует; остальное делает ядро.](assets/human-roles.svg)

Диаграмма «роли против видов» — это способ манифеста
сказать, что восемь принципов не являются девятью
принципами. Каждая роль — позиция человека; каждый вид —
позиция ядра; протокол распределяет работу так, чтобы
люди делали то, что могут делать только они (обязуют,
рецензируют, оперируют), а ядро делало всё остальное.

## Граница

![Граница между тем, что определяет ядро, и тем, что определяет человек. Ядро может проверять шесть вещей; шесть вещей решает только человек. Дословно из раздела Authority Boundary в spec/constitution.md.](assets/kernel-vs-human.svg)

Диаграмма «ядро против человека» — конституционный момент
манифеста. Шесть вещей, которые ядро может проверять;
шесть вещей, которые решает только человек. Граница —
центральное обязательство манифеста: с одной стороны
протокол подчиняется математике ядра, с другой —
человеческому суждению; обе стороны встречаются на шлюзе.

## Как читать этот сайт

Начните с [Methodology](methodology.html). Затем
[Axioms](axioms.html) для философских оснований. Затем
[Foundations](foundations.html) для отображения в OCaml.
Затем [Packages](packages.html) для живой поверхности
обеспечения качества.

Сам сайт порождён ядром (`mathc render`). Сетка пакетов
ниже — живой вывод `mathc packages`. Страницы, которые вы
читаете, — аргументы, которые ядро принимает о себе.

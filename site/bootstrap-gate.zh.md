# 引导闸门

> 引导闸门是内核判定从**人工声明**到**自动保证**的过渡。
> 本页是该过渡的公开记录。

## 问题所在

一个未被证明可工作的内核，就像是画在石头上的红绿灯。
在已发布的 3.0 内核成功检查本仓库及其一致性语料库之前，
内核的判定仍只是*人工声明*。它们或许诚实，但并无强制
力。

math-coding 3.0-alpha 便以这种状态诞生。从最初的提交
（`v3-alpha-0.0.1`，2026 年 9 月 26 日）到闸门失效的那一刻
（提交 `8fa7fcf`，2026 年 9 月 29 日），每项变更都必须满足
八项人工检查。该清单具有规范效力，并且只存一处：
`KERNEL_AGENTS.md` §Bootstrap gate。

这些检查在闸门失效时并不会被移除。它们仍是受保护策略
变更（对宪法、模式、规范化、内核、闸门规则、权限规则或
豁免规则的修改）的*附加*义务。对于日常工作——实践中
95% 的情形——由内核决定，由人工复核。

## 失效

闸门在提交 `8fa7fcf`（v3.0.0.19）失效。具体而言：

- `mathc self-check` 是阻塞性的 CI 步骤。在干净的 `main` HEAD
  上，此步骤输出 `self-check exit=0`，且 JSON 载荷中每个
  判定为 `Pass` 或 `Open_with_waiver` 的义务，其 `verdict`
  `unknown`（退出码 3）的 PR 将阻塞合并。主体的实时计数由
  `mathc self-check` 给出；主体在结构上不确定时可能仍为
  `unknown`，并在内核的豁免协商步骤中被映射为
  `Open_with_waiver`。
- 位于 `attestations/` 的证据存储为内核遍历器所枚举的
  每个决策-义务对保存一个 JSON 文件。实时计数来自
  `mathc counters --format=json`（`attestations.live_store`）。
- `mathc gate BASE HEAD` 针对已填充的存储报告判定：
  `gate-pass.t`、`gate-fail.t`、`gate-stale.t` 均为绿色。

自此提交起，**由 `mathc gate`、`mathc self-check` 和
`mathc assess` 产生的评估判定均为自动保证，而非人工声明**。

上面的时序图是引导闸门的标志性视觉。两条泳道：手动阶段
（顶部，每个 PR 八项人工检查）与自动阶段（底部，内核驱动

被允许。

## 失效后的八项检查

对于受保护策略的变更，八项人工检查依然具有约束力。它们
记录在 `KERNEL_AGENTS.md §Self-application`，并由公理 A3 管辖
（规则管理自身的变更）。内核自动强制执行常规检查，人工
强制执行宪法层面的检查。两种阶段并存。

八项人工检查是受保护变更的*附加*义务，而非相互竞争的义务。
对内核、闸门规则、模式、宪法或豁免规则的修改仍由人工把关；
对用户项目的修改（实践中 95% 的情形）由 `mathc self-check`
把关。上图在同一张图中同时呈现两种阶段；这正是关键所在。
引导闸门并未移除八项检查，而是在它们之上叠加了自动阶段。

## 本站点是什么

本站点是闸门失效**之后**内核产生的第一件制品。其上的每
一页都由 `mathc render` 从 `site/` 下的源文件渲染而成。
[index.html](index.html) 上的包网格是
`mathc packages --format=html` 的实时输出。方法论页面
（[methodology.html](methodology.html)）描述了内核所强制
执行的纪律；内核在描述该纪律的站点上强制执行它本身。
这便是 A3 的具体应用。

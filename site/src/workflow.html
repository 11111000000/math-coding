Workflow

The format of specifications and evidence is version 6; the tool is mathc 5 — the product version did not change. The main loop is init, goal, add, run and map; next names one concrete next action. Reading verbs never modify the working tree; controls run in isolated copies; human decisions are recorded explicitly with an author and decision-specific data. mathc help COMMAND describes each verb and works before any specification exists. The full model is in the canonical methodology (Russian).

The main loop

An example loop in a project whose claim is confirmed:

$ mathc init $ mathc goal "payments stay idempotent" "src/,test/" "anna" $ mathc add retry-safety "a retried charge is never applied twice" \ src/payments.ml,test/payments.ml \ "a duplicate charge passes the suite" fact \ --requirement "verifier:dune runtest test/payments.exe" \ --control "sed -i 's/dedupe//g' src/payments.ml" $ mathc run $ mathc map verdict: green retry-safety holds $ mathc next next: nothing to do - declared evidence is current and the tree is covered

What a run of format 6 can do

A run of format 5 executed every declared check and wrote the evidence down. A run of format 6 does more and says more.

whathow
partial runmathc run --changed executes only the claims whose evidence no longer holds and leaves the rest as they are
priceevery run writes what it cost into the journal of the runs: machine seconds per claim, the slowest first (.math/v6/runs.jsonl)
limitmathc run --limit SECONDS bounds the run; 3600 seconds by default
a stopped runit says that it was stopped, hands over the map over what it observed, and exits with code 4

The control must be the cause

The control proves that a check can reject one concrete violation, and for that the check has to run in the copy before the control is applied. The protocol: the same check must first pass on an untouched copy of the subject; only then is the control applied and the check repeated, and it must return an ordinary fail. A copy that cannot run the check at all — missing dependencies, no toolchain — proves nothing by failing: the observation becomes inconclusive with the reason copy-failed, and a machine holds is then impossible.

A check that needs the dependencies of the project declares the environment it runs in: the environment prefix (--environment ENV on add) prepares that environment before the check runs. Without the declaration the copy cannot run the check, and the reason copy-failed says so instead of a false proof.

The environment and the build of the tool

In format 5 the fingerprint of the environment included the digest of the binary, so rebuilding the tool made every piece of evidence everywhere stale at once: in one project 151 confirmations went stale although none of them had become false. In format 6 the environment is the operating system and the pinned toolchain (the lock file), and the build of the tool is written separately, next to the environment. A tool change is named tool-changed and does not revoke the result: the check was the same and the subject was the same.

Linking an ADR

ADRs keep motivation and history; math-coding never writes into them. import-adr prints a draft, adopt lists discovered sources, and only an explicit add --source binds a claim to the document — by digest.

Human decisions

  • mathc record ID AUTHORITY --by WHO --outcome OUTCOME — records an external review for a declared review:AUTHORITY requirement. Exactly five outcomes exist: pass, fail, inconclusive, infrastructure-error, not-run.
  • mathc waive ID --by WHO --reason WHY --valid-for DAYS --recovery ACTION — a bounded risk acceptance. It is not a pass and never covers a failure.
  • mathc authorize --by WHO --reason WHY — works only with a policy.json; it is a permission log, not authentication.
  • mathc approve --by WHO --reason WHY [--command CMD] — approves the commands the agent surface may execute in this project. Without an approval the surface refuses to declare or to run a command, and names it.
  • mathc install refreshes the marked block in AGENTS.md; mathc doctor checks the setup and fixes nothing.

The rest of the verbs

The loop above is the daily work. The remaining verbs serve the edges of a project, and none of them changes the working tree unless it says so.

A claim with the register judgment is established only by an external human review: add requires review:WHO for it and refuses machine verifiers.

Upgrading a project of format 5

  1. Update the tool of the project first — its installed binary and its CI. The tool that reads a project must understand format 6 before the migration lands in the tree: the previous version cannot read a specification of version 6, and the gate of the project fails with unsupported schema_version 6.
  2. Then mathc migrate — the journals move to .math/v6/, and the old files stay on disk.
  3. Then mathc run again — the evidence is written anew.

The order was found by the field measurement of 2026-11-22 and corrected in the plan of the architecture.

Reading the map without the terminal

The map can also be read in a browser. The console shows the same map, the queue of the human and the journal of observations, and it never computes a state of its own. The interfaces, piece by piece.

Exit codes

codemeaning
0green, or the action succeeded
1red, or a protected transition was refused
2invocation error
3unknown or vacant — the state is not established
4the run was stopped — it says so and hands over the map over what it observed
5the tool could not answer — a broken specification or a broken repository

A corrupted evidence trail is neither ignored nor treated as absence of evidence. mathc help COMMAND prints the exact codes per verb.

Code 3 and code 5 are not the same answer. Code 3 says that the state is not established yet; code 5 says that the tool could not answer at all. A consumer that reads a broken tool as an unfinished project will wait for work that will never arrive.

Minimal sufficient friction: ordinary work needs no paperwork per file. Structure is added only where a measured benefit exists.

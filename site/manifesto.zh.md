# 宣言

> **八条原则，一个静态二进制。** math-coding 是一门在
> 编写代码之前先记录决策的纪律，内核强制该记录得到遵守。

## 它是什么？它与其他方法论有何不同

mathcoding 是一项面向软件变更的保障协议：每一项变更都
绑定于一项有记录的义务、一份带边界的证据、以及内核给出
的确定性判定（`pass`、`fail`、`inconclusive`……）。它既不
是 CI，也不是「文档即代码」，更不是「LLM 当裁判」；最
接近的邻人是 Spec-Driven Development 与 ADR/MADR。与二十
种方法论的逐条对比见 [区别](differences.html)。

## 为何存在

决策会被遗忘 —— 但不是因为没人写下来。恰恰相反：
有人写下了 `decisions/decision.yaml`、
`decisions/adoption-friction-p0-2026-10.yaml`，有人在 CI 里接了 LLM 当裁判。
但到第三个版本发布时，当初的理由已经无法重建，只能
靠考古。代码之所以偏离初衷，是因为我们把两件不同的
事混为一谈 —— 记录决策与验证决策。惯用的工具都不能
区分这两件事。

最接近的三种做法，对这种混淆没有给出回答：

- **ADR（Nygard / MADR）。** 决策以 Markdown 记录——
  但缺少将 ADR 与代码相互核对的闸门。记录静默地老
  化；「Status: superseded」始终只是一行字符串，
  而非版本 DAG 中的一条边。
- **Spec-Driven Development**（GitHub Spec Kit、AWS Kiro，
  2025）。规范先于代码 —— 但规范并不绑定到验证器。
  没有通过测试的规范被视为「已采纳」；形式上的契合
  被冒充为验证。
- **LLM 当裁判。** 模型给出判定 —— 但没有来源种类、
  没有输入，也没有时间边界。在它的输出里，「已核对」
  与「未核对」无法区分：模型的判定是 `reviewed`，
  而不是 `observed`。

三者共享同一种混淆：把「已记录」冒充为「已验证」。
mathcoding 把这两件事放在协议的两侧，再以「义务、
证据、判定」重新串起来。没有证据，义务就是
`inconclusive`。「我没核对」并不等于「我核对了，
没问题」。

math-coding 翻转了这一不对称：每一项架构承诺都在代码
之**前**写下，内核在每次合并时核对承诺与代码是否一致。
这门纪律称为 **mathcoding**。^[在工作纪律中，能闭合
反馈回路的最小元素，就是一个验证器 —— 一段可以重复
运行、且退出码表示「过」或「败」的程序。]

![math-coding 架构：围绕人类的五个同心层 —— 公理、内核、协议对象、站点与工具、用户项目。](assets/architecture-overview.svg)

上面的架构图是本宣言的心智模型。人类居于中心：每
一次对 math-coding 自身的变更、对内核的变更、对协议
对象的变更、对站点与工具的变更、对用户项目的变更，
都由同一个 math-coding 把关。协议以五个同心层环绕
人类；任何东西都无法绕过闸门。

## 它不是什么

- 不是 CI 运行器。请使用 `scripts/dev` 或 GitHub Actions。
- 不是文档生成器。规范才是规范性的；工具读取规范。
- 不是代码评审工具。请使用 `paseo` 智能体或 GitHub PR
  评审。
- 不是运行时监控器。内核离线运行；证据在带外生成。

内核的工作是**保障回路**：每一项承诺都有一条通向观察
的路径；每一个观察都对应一个已知的来源种类；每一个
来源种类都受主体、输入与时间的约束。

![人在回路中：三个角色（作者、评审者、运营者）触及协议中的五点。第五点（签署证据或授予豁免）是内核唯一无法替代的点。](assets/human-in-the-loop.svg)

上面的「人在回路中」图，是本宣言对「在自动化协议中，
人类的位置在哪里？」这个问题的回答。答案是：三个
角色，五处要点。内核是地板，人类是天花板。

## 原则

内核核查每个生效决策中所声明的义务，全部以数据包形式记录于
`decisions/`。其中八个数据包构成了闭合引导回路的最小集合。
规范清单是主策略在 `decisions/decision.yaml` 中的义务；
公理 → 内核机制 → 验证义务的映射见
[Foundations](foundations.html)。

这八条并非随意选出。它们是闭合引导回路的最小集合：
从首个提交（`v3-alpha-0.0.1`）到内核能检查自身的时刻
（提交 `8fa7fcf`），每一项变更都必须获得这八条的同时
通过。如今两端皆已达成。完整的实时清单见
[Packages](packages.html)。

![人类角色与对象种类的对应关系：哪个角色触及七个种类中的哪一个。作者创造，评审者评审，运营者运营；其余由内核处理。](assets/human-roles.svg)

「角色 vs 种类」图，是本宣言用以说明「八条原则不是九条
原则」的方式。每个角色是人类的位置；每个种类是内核的
位置；协议将工作划分得让人类去做唯有他们能做的事
（承诺、评审、运营），而内核承担其余一切。

## 边界

![内核侧与人类侧之间的边界：内核可检查六件事；唯有六件事只能由人类决定。本图逐字取自 spec/constitution.md 的 Authority Boundary 一节。](assets/kernel-vs-human.svg)

「内核 vs 人类」图，是本宣言的宪法性瞬间。内核可检查
六件事；唯有六件事只能由人类决定。边界是宣言的核心
承诺：协议在一侧由内核以数学方式核对、在另一侧由人类
判断，两侧在闸门上相遇。

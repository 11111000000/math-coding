# Отличия — как mathcoding сравнивается с другими методологиями

> **О чём эта страница.** Поточечное сравнение mathcoding с
> методологиями, которые наиболее на него похожи:
> разработка через спецификации, записи архитектурных решений,
> предметно-ориентированное проектирование, разработка через
> поведение, формальные методы, архитектурные фреймворки и
> модели зрелости обеспечения качества. В каждом разделе
> названо, что другая методология делает хорошо, и что
> mathcoding добавляет, отказывается делать или меняет.

## Ответ одной строкой

**mathcoding — это протокол обеспечения качества, а не язык
спецификаций и не система документации.** Большинство
методологий описывают, *что* нужно построить или *как* должна
работать команда. mathcoding привязывает каждое изменение к
записанному обязательству, списку обязательств, ограниченному
свидетельству и вердикту, который вырабатывается детерминированным
ядром. Там, где другие методологии могут дрейфовать, mathcoding
не может — ядро либо пропускает изменение, либо нет, и
вердикт ссылается на правило, субъект, причину и средство
исправления.

## Три свойства, которые ни одна методология не сочетает

mathcoding — это не сумма возможностей из других методологий.
Это конкретное сочетание трёх свойств, которые никакая другая
методология не предлагает вместе:

1. **Ограниченное свидетельство.** Каждое заявление ограничено
   субъектом, обязательством, входами, средой, дайджестом
   реализации, методом и временем. Заявление без ограничений —
   это не заявление, а выражение намерения.
2. **Честная неопределённость.** Отсутствие свидетельства —
   это `Inconclusive`, а не `Pass`.
   `Pass ≠ Fail ≠ Inconclusive ≠ InfrastructureError`.
   `Waived ≠ Pass`. `Reviewed ≠ Observed`. Пять классов
   источников (`declared ≠ derived ≠ attested ≠ reviewed ≠
   observed`) не могут быть сведены друг к другу.
3. **Само-применение.** Правила, управляющие mathcoding,
   управляют самим mathcoding. Изменение конституции, схем,
   ядра или правил шлюза является *переходом защищённой
   политики* и требует решения по прежней политике, сильнейшего
   контрпримера, позитивных и негативных фикстур, пути
   миграции, пути восстановления, санкционирования прежней
   политикой и списка изменённых вердиктов.

Если какая-то методология предлагает одно из этих свойств —
mathcoding наследует этот кусок. Если она предлагает два —
mathcoding делает третье строже. Если предлагает все три — эта
методология либо mathcoding, либо его потомок.

## Сравнение с высоты птичьего полёта

| Методология | Что она утверждает | Что добавляет mathcoding |
|---|---|---|
| TDD | Тесты предшествуют коду | Тесты проверяют обязательства, а не поведения; обязательства версионируются и проверяемы |
| BDD | Поведение выражается в форме `Given/When/Then` | Поведения недостаточно; ядро спрашивает, кто его наблюдал и когда |
| DDD | Код отражает предметную область | Доменная модель — один из видов решений; ядро пропускает изменения через шлюз |
| FDD | Фичи — единица планирования | Фича — это решение; обязательство — то, что фича должна сохранить |
| MDD / MDA | Модели порождают код | Модели — это свидетельство, а не источник истины; источник истины — решение |
| Spec-Driven Development | Спецификации предшествуют коду | Спецификация без аттестации — пожелание; mathcoding замыкает петлю |
| ADR (Nygard / MADR) | Решения записываются в Markdown | Запись — это YAML-пакет со схемой, обязательством и проверяемым вердиктом |
| arc42 | Двенадцать разделов архитектурной документации | Каждый раздел — необязательное обязательство; ничего не требуется, пока активная политика не потребует |
| C4 Model | Диаграммы на четырёх уровнях приближения | Диаграммы — это свидетельство класса `attested`; обязательство — свойство, которое диаграмма должна сохранить |
| Living Documentation | Документация генерируется из кода | Живая документация — один из классов источников; mathcoding допускает и другие |
| Specification by Example | Примеры закрепляют контракт | Примеры — один из видов аттестации; контракт — обязательство, пример — свидетель |
| OpenAPI | API описан в машиночитаемой форме | Описание — это одно обязательство; остальные покрывают поведение, безопасность, свежесть |
| Design by Contract | Предусловия и постусловия на каждом вызове | Контракты — это обязательства на функции; mathcoding добавляет обязательства на решения, аттестации и waiver'ы |
| Formal Methods (TLA+, Coq, …) | Свойства доказаны в ассистенте доказательств | Доказательство — один из видов аттестации; обязательство может быть класса review, test или observation |
| TOGAF | Фреймворк архитектуры предприятия | mathcoding — это шлюз; TOGAF описывает метамодель, которую шлюз читает |
| ISO/IEC/IEEE 42010 | Стандарт описания архитектуры | 42010 называет интересы; mathcoding привязывает каждый интерес к обязательству и верификатору |
| Team Topologies | Организационная структура для разработки ПО | Team Topologies называет когнитивную нагрузку; mathcoding называет трение на одно изменение, которое эта нагрузка порождает |
| SAFe | Масштабированный agile-процесс | SAFe называет церемонии; mathcoding привязывает артефакт каждой церемонии к верификатору и аттестации |
| OWASP SAMM | Модель зрелости обеспечения качества ПО | SAMM оценивает организацию; mathcoding оценивает каждое изменение |
| NIST SSDF | Практики безопасной разработки ПО | SSDF называет практики; mathcoding делает каждую практику проверяемой для каждого изменения |

Таблица — это сводка. Разделы ниже раскрывают каждую строку.

## 1. TDD — разработка через тестирование (Kent Beck, 2002)

TDD пишет падающий тест, делает его проходящим, затем
рефакторит. Дисциплина локальна для единицы кода; тест — это
контракт; рефакторинг — это свобода менять реализацию, не
ломая контракт.

**Что наследует mathcoding:** идею «тест как свидетельство».
Аттестация mathcoding с `kind: test` — это, на уровне
протокола, TDD-тест, повышенный до артефакта первого класса:
она несёт идентификатор производителя, метод, дайджест
реализации и вердикт.

**Что добавляет mathcoding:** тест привязан к конкретному
`обязательству`, а не к поведению. Обязательство называет
*свойство*, которое тест должен сохранить; тест называет
*проверку*, которую ядро выполняет. Если тест проходит, но
обязательство не упомянуто ни в одном активном решении, тест
не участвует в петле обеспечения — он остаётся внутренним
артефактом. TDD трактует каждый тест как контракт; mathcoding
требует, чтобы контракт был задекларирован в решении.

**От чего отказывается mathcoding:** от неявного утверждения
«тесты прошли — значит система корректна». В mathcoding `pass` —
это вердикт одного обязательства; зелёный набор тестов —
свидетель, а не вердикт.

## 2. BDD — разработка через поведение (Dan North, 2003)

BDD выражает поведение в форме `Given / When / Then`, причём
сценарий записан на подмножестве естественного языка, которое
команда разделяет с бизнесом. Дисциплина — это сценарий;
исполнитель — Cucumber, SpecFlow или Behave.

**Что наследует mathcoding:** идею «сценарий как спецификация».
Обязательство mathcoding может быть выражено в виде сценария
`Given/When/Then` в поле `verifier: bdd-scenario`. Ядро
принимает сценарий, связывает его с обязательством и
трактует исход сценария как вердикт обязательства.

**Что добавляет mathcoding:** исход сценария — одно из пяти
значений, а не двух. `Pass`, `Fail`, `Inconclusive`,
`InfrastructureError` и `Waived` различаются; проходящий
сценарий без запуска исполнителя — это `Inconclusive`, а не
`Pass`. BDD смешивает «сценарий проходит, когда запущен» с
«поведение проверено»; mathcoding держит эти две вещи порознь.

**От чего отказывается mathcoding:** от предположения, что
бизнес-читаемый сценарий — это верификация. Сценарии легко
читать и трудно верифицировать; mathcoding трактует их как
один из видов аттестации, с обычными ограничениями по
`producer_identity` и `environment`.

## 3. DDD — предметно-ориентированное проектирование (Eric Evans, 2003)

DDD моделирует код на предметной области: ограниченные
контексты, единый язык, агрегаты, доменные события.
Дисциплина *разговорная*; артефакты — это код, диаграммы и
глоссарий.

**Что наследует mathcoding:** дисциплину именования вещей
так, чтобы ядро и люди согласовались. Решение mathcoding несёт
`намерение` и `обязательство`; оба записываются на едином
языке команды.

**Что добавляет mathcoding:** ядро не знает предметную
область; оно знает решение. Ограниченный контекст — это одно
решение; единый язык — это свойство, разделяемое решениями;
агрегат — это пространство имён путей, которое шлюз защищает.
DDD называет форму; mathcoding обеспечивает шлюз на этой
форме.

**От чего отказывается mathcoding:** от предположения, что
хорошо смоделированная область — это проверенная система.
Корректная модель без обязательств — пожелание; корректная
модель с обязательствами, но без аттестаций — гипотеза.
mathcoding требует третий артефакт.

## 4. FDD — разработка по фичам (De Luca & Coad, 1997)

FDD строит систему фича за фичей; каждая фича ограничена,
спроектирована и реализована небольшой командой. Дисциплина —
это список фич; артефакт — это работающее приращение.

**Что наследует mathcoding:** фичу как единицу планирования.
Решение mathcoding может объявить `feature_id`; обязательство —
это свойство, которое фича должна сохранить.

**Что добавляет mathcoding:** фича несёт `верификатор` и
`вердикт`. FDD отслеживает прогресс; mathcoding отслеживает
верификацию. Ядро измеряет не скорость, а вердикты
обязательств.

**От чего отказывается mathcoding:** от неявного утверждения
«фича построена — значит фича проверена». Сборка — это
`изменение`; верификация — это `аттестация`; два — разные
виды.

## 5. MDD / MDA — разработка, управляемая моделями (OMG, 2001)

MDD/MDA порождает код из платформо-независимых моделей (PIM)
и платформо-зависимых моделей (PSM). Дисциплина — это модель;
артефакт — порождённый код.

**Что наследует mathcoding:** модель как артефакт первого
класса. Решение mathcoding может объявить поле `model`; модель
— одна из подложек, дайджест которых вычисляет ядро.

**Что добавляет mathcoding:** модель — это свидетельство, а не
источник истины. Источник истины — решение; модель — один из
видов аттестации. Если модель и код расходятся, проигрывает код
(потому что обязательство — это свойство, которое должен
удерживать код, а не свойство, которое должна удерживать
модель). MDD/MDA трактует модель как источник; mathcoding
трактует модель как одного из свидетелей.

**От чего отказывается mathcoding:** от предположения, что
порождённый код — это проверенный код. Генератор — это метод;
порождённый артефакт — это дайджест; верификация — отдельная
аттестация.

## 6. Spec-Driven Development (GitHub Spec Kit, AWS Kiro, 2025)

Spec-Driven Development (SDD) — это индустриальный термин
2025 года для методологий, которые начинаются со
спецификации: файл Markdown, описывающий фичу, критерии
приёмки и план тестирования. GitHub Spec Kit, AWS Kiro, GitLab
Duo и ряд коммерческих агентов кодинга принимают эту форму.
Дисциплина — это спецификация; артефакт — спецификация плюс
порождённый код.

**Что наследует mathcoding:** идею «спецификация как
источник истины». `Обязательство` решения mathcoding — это, в
смысле уровня протокола, спецификация — опровержимое
заявление о свойстве изменения.

**Что добавляет mathcoding:** спецификация привязана к
*верификатору* и *вердикту*. SDD порождает спецификацию и
изменение кода; спецификация проверяется тестами, но тесты
не привязаны к спецификации самой методологией. Спецификация
может быть соблюдена только формально; обязательство
mathcoding не может — ядро проверяет аттестацию на каждом
шлюзе.

**От чего отказывается mathcoding:** от неявного утверждения
«спецификация написана — значит это верификация». В SDD
«спецификация написана» — это веха; в mathcoding «спецификация
написана» — это начало петли, а не её конец. Спецификация без
проходящей аттестации — это `Inconclusive`-обязательство, а
не `Pass`.

**Это ближайший живой конкурент.** SDD — та же форма без
дисциплины ограниченного свидетельства. Если вы читаете SDD и
думаете «это было бы лучше с видами аттестаций, истечением
waiver'ов и детерминированным шлюзом», — вы прочитали дельту
mathcoding.

## 7. ADR — записи архитектурных решений (Michael Nygard, 2011; MADR, 2018)

ADR записывает каждое значимое архитектурное решение как
короткий файл Markdown с полями `Context`, `Decision`,
`Consequences` и `Status`. MADR расширяет формат вариантами,
драйверами решений и процессом подтверждения. Дисциплина —
это запись; артефакт — файл.

**Что наследует mathcoding:** идею «решение как артефакт».
`Решение` mathcoding — это форма ADR со схемой, обязательным
списком обязательств и детерминированным шлюзом. `mathc
import-adr` — это инструмент первого класса, который
преобразует файлы MADR и adr-tools в пакеты mathcoding.

**Что добавляет mathcoding:** решение несёт `обязательства` и
`аттестации`. Ядро проверяет каждое решение относительно его
обязательств на каждом шлюзе; решение без обязательства —
информационное, а не блокирующее; решение с обязательством и
без аттестации — `Inconclusive`. ADR — это блокнот; mathcoding
— это блокнот со средством проверки.

**От чего отказывается mathcoding:** от предположения, что
написанный ADR — это проверенный ADR. Блок `Context / Decision
/ Consequences` — это декларация; ядро читает декларации и
спрашивает: «какое свидетельство, что декларация всё ещё
действует?». Ответ — аттестация.

**Это ближайший структурный конкурент.** ADR — это исток
mathcoding. Там, где ADR человеко-читаем и нетипизирован,
mathcoding машино-читаем, валидируется схемой и проверяется
шлюзом. Там, где в ADR «Status: superseded» — это строка, в
mathcoding `supersedes` — это отношение на DAG ревизий, по
которому ядро проходит.

## 8. arc42 — двенадцать разделов архитектурной документации (Gernot Starke, Peter Hruschka)

arc42 — это шаблон документации программной архитектуры:
двенадцать разделов от `Introduction and Goals` до `Risks and
Technical Debts`. Дисциплина — это шаблон; артефакт — это
заполненный документ.

**Что наследует mathcoding:** идею «раздел как пространство
имён». Решение mathcoding может объявить `arc42_section`;
обязательство — свойство, которое этот раздел должен
сохранить.

**Что добавляет mathcoding:** раздел не требуется, пока
активная политика его не потребует. arc42 поставляет
двенадцать разделов; mathcoding поставляет ноль разделов и
просит активную политику объявить, какие из них проект
считает важными. Позиция «пусто по умолчанию» — это аксиома
A0 Разделение в действии: виды различны, и документация —
другой вид, нежели решение.

**От чего отказывается mathcoding:** от предположения, что
заполнение шаблона — это верификация. Шаблон — это структура;
верификация — это верификатор. mathcoding заменяет структуру
проверкой.

## 9. C4 Model — Context, Containers, Components, Code (Simon Brown, 2011)

C4 — это иерархическая схема диаграмм: контекст системы,
контейнеры, компоненты, код. Дисциплина — это диаграмма;
артефакт — набор диаграмм.

**Что наследует mathcoding:** идею «уровень приближения».
Решение mathcoding может объявить `c4_level`; обязательство —
свойство, которое диаграмма на этом уровне должна сохранить.

**Что добавляет mathcoding:** диаграмма — это `аттестация`, а
не `решение`. Диаграмма может засвидетельствовать, что
система имеет определённую форму; решение объявляет форму,
обязательство называет свойство, диаграмма — свидетель. C4
смешивает форму со свидетелем; mathcoding разделяет их.

**От чего отказывается mathcoding:** от предположения, что
актуальная диаграмма — это проверенная диаграмма. Диаграмма
стареет; обязательство — нет. Поле `valid_until` на
обязательстве — то, что делает диаграмму честной во времени.

## 10. Living Documentation (Cyrille Martraire)

Living Documentation — это практика генерации документации из
кода: тестов, типов, примеров, сценариев. Дисциплина — это
генератор; артефакт — документация.

**Что наследует mathcoding:** идею «документация как
побочный продукт». Аттестация mathcoding может нести поле
`producer: living-doc`; живая документация — один из видов
аттестации.

**Что добавляет mathcoding:** живая документация — один из
пяти классов источников, а не единственный. `declared`
(советник), `derived` (генератор), `attested` (тест),
`reviewed` (человек), `observed` (среда исполнения) — разные;
mathcoding допускает все пять и отказывается повышать
`derived`-заявление до `observed` без артефакта.

**От чего отказывается mathcoding:** от предположения, что
сгенерированный документ — это проверенный документ.
Генератор — это метод; вывод — это дайджест; верификация —
отдельная аттестация.

## 11. Specification by Example (Gojko Adzic)

Specification by Example (SBE) записывает контракт как
примеры: входы, выходы, граничные случаи. Дисциплина — это
пример; артефакт — исполнимая спецификация.

**Что наследует mathcoding:** идею «пример как спецификация».
Обязательство mathcoding может быть выражено как набор
примеров в `acceptance.examples`; ядро принимает примеры и
трактует каждый как фикстуру.

**Что добавляет mathcoding:** пример — один из видов
аттестации, а не единственный. SBE трактует пример как
верификацию; mathcoding трактует пример как свидетеля, а
обязательство — как контракт. Два — разные виды.

**От чего отказывается mathcoding:** от предположения, что
проходящий набор примеров — это проверенная система. Набор
примеров ограничен входами; обязательство — нет. Изменение,
которое сохраняет набор примеров, но нарушает свойство,
названное в обязательстве, — `Fail` в mathcoding и `Pass` в
SBE.

## 12. OpenAPI — машиночитаемая спецификация API

OpenAPI описывает HTTP-API в YAML или JSON: пути, методы,
параметры, ответы, схемы. Дисциплина — это описание; артефакт
— файл спецификации и сгенерированные клиент/сервер.

**Что наследует mathcoding:** идею машиночитаемого контракта.
Решение mathcoding может объявить `openapi_spec`; обязательство
— свойство, которое API должен сохранить.

**Что добавляет mathcoding:** спецификация OpenAPI — это одно
обязательство; остальные обязательства покрывают поведение,
безопасность, свежесть и обратную совместимость. OpenAPI
описывает форму; mathcoding привязывает форму к верификатору
и вердикту. Зелёный OpenAPI-линт — это `Inconclusive`-
обязательство, а не `Pass` — контракт может быть выполнен,
пока поведение — нет.

**От чего отказывается mathcoding:** от предположения, что
сгенерированный клиент — это проверенный клиент. Генератор —
это метод; сгенерированный артефакт — это дайджест;
верификация — отдельная аттестация.

## 13. Design by Contract (Bertrand Meyer, Eiffel, 1986)

Design by Contract (DbC) прикрепляет предусловия,
постусловия и инварианты к каждой операции. Дисциплина — это
контракт; артефакт — код с контрактами, записанными
непосредственно в нём.

**Что наследует mathcoding:** идею «контракт как свойство».
Обязательство mathcoding может быть выражено как поле
`dbc:precondition` или `dbc:postcondition`; ядро принимает
контракт и трактует проверку во время исполнения как
верификатор.

**Что добавляет mathcoding:** контракт — на *решении*, а не
на функции. Решение несёт одно или несколько обязательств;
каждое обязательство может быть выражено как DbC-контракт.
mathcoding добавляет обязательства на аттестации, на waiver'ы,
на ревизии — виды, которых у DbC нет. DbC — это дисциплина
контрактов; mathcoding — дисциплина контрактов плюс
дисциплина верификаторов плюс дисциплина восстановления.

**От чего отказывается mathcoding:** от предположения, что
проходящая DbC-проверка во время исполнения — это проходящая
система. Проверка во время исполнения — один из видов
аттестации, ограниченный входами, которые её вызвали;
обязательство — нет. Изменение, которое сохраняет проверку
DbC, но нарушает свойство, названное в обязательстве, —
`Fail` в mathcoding и `Pass` в DbC.

**Это структурно близкий сосед.** DbC и mathcoding разделяют
взгляд на корректность через свойства. Разница в том, что
свойства mathcoding лежат на решениях, аттестациях и
waiver'ах — не только на функциях.

## 14. Formal Methods — TLA+, Coq, Isabelle, Lean, Alloy

Формальные методы выражают спецификацию на формальном языке
и доказывают (или проверяют на модели) её свойства.
Дисциплина — это доказательство; артефакт — скрипт
доказательства и сертификат.

**Что наследует mathcoding:** идею «доказательство как
свидетельство». Аттестация mathcoding может нести поле
`producer: tla+ | coq | isabelle`; доказательство — один из
видов аттестации.

**Что добавляет mathcoding:** доказательство — один из видов
аттестации, а не единственный. Формальное доказательство —
это аттестация `Pass`; неформальный обзор — аттестация
`Review`; наблюдение во время исполнения — аттестация
`Observed`. Три — разные; mathcoding допускает все три и
отказывается повышать `Review` до `Observed` без артефакта.

**От чего отказывается mathcoding:** от предположения, что
доказанное свойство — это проверенная система. Доказательство
ограничено моделью; модель ограничена спецификацией;
спецификация ограничена решением. Доказанное свойство в
модели, не совпадающей с решением, — `Stale` в mathcoding:
аттестация честна, подложка изменилась, ядро переоценивает.

**Это глубочайший сосед.** Формальные методы и mathcoding
разделяют дисциплину ограниченного свидетельства. Разница в
охвате: формальные методы доказывают свойства модели;
mathcoding привязывает решение к верификатору любого вида
(тест, обзор, наблюдение, доказательство, сигнал исполнения)
и отказывается повышать вердикты между видами.

## 15. TOGAF — фреймворк архитектуры предприятия Open Group

TOGAF — это фреймворк архитектуры предприятия: Architecture
Development Method (ADM), Architecture Content Framework,
Enterprise Continuum. Дисциплина — цикл ADM; артефакт —
описание архитектуры.

**Что наследует mathcoding:** идею «архитектура как
содержимое». Решение mathcoding может объявить `togaf_phase`;
обязательство — свойство, которое должна породить эта фаза.

**Что добавляет mathcoding:** TOGAF называет фазу; mathcoding
называет верификатор. Фаза A TOGAF (Architecture Vision) без
верификатора — пожелание; решение mathcoding, которое называет
фазу A и объявляет верификатор, — проверка. TOGAF — это
метамодель; mathcoding — шлюз, который читает метамодель.

**От чего отказывается mathcoding:** от предположения, что
завершённый цикл ADM — это проверенная архитектура. Цикл — это
процесс; верификация — поартефактна. mathcoding заменяет цикл
поартефактными обязательствами.

## 16. ISO/IEC/IEEE 42010 — стандарт описания архитектуры

ISO/IEC/IEEE 42010 — это международный стандарт описания
архитектуры: заинтересованные лица, интересы, точки зрения,
представления, правила соответствия, языки. Дисциплина — это
описание архитектуры; артефакт — документ описания архитектуры.

**Что наследует mathcoding:** идею «интерес как свойство».
Обязательство mathcoding может объявить
`iso42010_concern`; обязательство — свойство, которое
архитектура должна удовлетворять для этого интереса.

**Что добавляет mathcoding:** 42010 называет интерес;
mathcoding привязывает интерес к верификатору. Описание
архитектуры, соответствующее 42010, без верификаторов — это
документ; решение mathcoding, которое называет интерес и
верификатор, — это проверка. 42010 — метамодель; mathcoding —
шлюз.

**Это глубочайший стандартизационный сосед.** 42010 и
mathcoding разделяют интерес-ориентированный взгляд на
архитектуру. Разница в виде обязательства: обязательства
42010 лежат на описании; обязательства mathcoding лежат на
изменении, аттестации, waiver'е и ревизии.

## 17. Team Topologies (Matthew Skelhorn, Manuel Pais)

Team Topologies — это организационное устройство для команд
разработки: четыре типа команд (stream-aligned, enabling,
complicated-subsystem, platform), три режима взаимодействия
(collaboration, X-as-a-Service, facilitating) и модель
когнитивной нагрузки. Дисциплина — топология команд;
артефакт — топология команд и межкомандные протоколы.

**Что наследует mathcoding:** модель когнитивной нагрузки.
`Режим` mathcoding (tiny / light / standard / strict /
exhaustive) — это функция риска, который сам — функция
когнитивной нагрузки, которую изменение возлагает на
команду.

**Что добавляет mathcoding:** Team Topologies называет
нагрузку; mathcoding называет трение, которое эта нагрузка
порождает. Изменение, которое Team Topologies классифицирует
как `facilitating`, в mathcoding — это трение уровня `record`;
изменение, пересекающее границу команд, — трение уровня
`ask`; изменение конституционного правила — трение уровня
`block`. Две системы отображаются друг в друга, но трение
mathcoding — поизменёнческое, а не покомандное.

**От чего отказывается mathcoding:** от предположения, что
хорошо структурированная команда — это проверяющая команда.
Структура — свойство организации; верификация — свойство
изменения. Изменение в stream-aligned команде — `Inconclusive`,
если аттестация отсутствует, независимо от структуры команды.

## 18. SAFe — масштабированный agile-фреймворк

SAFe — это фреймворк масштабирования agile: уровни
конфигурации (Essential, Large, Portfolio), роли, церемонии,
артефакты. Дисциплина — каденция церемоний; артефакт — план
Program Increment (PI) и выходы итераций.

**Что наследует mathcoding:** идею каденции. Решение mathcoding
может объявить `safe_pi`; обязательство — свойство, которое
должен сохранить PI.

**Что добавляет mathcoding:** SAFe называет церемонию;
mathcoding привязывает артефакт к верификатору. План PI без
верификатора — пожелание; решение mathcoding, которое
называет артефакт PI и объявляет верификатор, — это
проверка. SAFe — процесс; mathcoding — поартефактная
проверка.

**От чего отказывается mathcoding:** от предположения, что
завершённый PI — это проверенный PI. PI — результат
процесса; верификация — поартефактна. mathcoding заменяет
процессный шлюз поартефактными обязательствами.

## 19. OWASP SAMM — модель зрелости обеспечения качества ПО

OWASP SAMM — это модель зрелости для обеспечения качества ПО:
пять бизнес-функций (Governance, Design, Implementation,
Verification, Operations), каждая с тремя практиками
безопасности, каждая с тремя уровнями зрелости. Дисциплина —
лестница зрелости; артефакт — оценка SAMM.

**Что наследует mathcoding:** идею функции обеспечения
качества. Решение mathcoding может объявить
`samm_function`; обязательство — свойство, которое должна
удовлетворять функция.

**Что добавляет mathcoding:** SAMM оценивает организацию;
mathcoding оценивает каждое изменение. Организация уровня
SAMM-3 может выпустить изменение, обязательства которого —
`Inconclusive`; организация уровня SAMM-1 может выпустить
изменение, обязательства которого — `Pass`. Вердикт —
поизменёнческий, а не поорганизационный.

**От чего отказывается mathcoding:** от предположения, что
зрелая организация — это проверяющее изменение. Зрелость —
свойство организации; верификация — свойство изменения. Два
— разные виды.

**Это ближайший сосед по зрелости обеспечения.** SAMM и
mathcoding разделяют лексику обеспечения качества. Разница
в зернистости: SAMM — ежегодный и поорганизационный;
mathcoding — поизменёнческий и пообязательственный.

## 20. NIST SSDF — фреймворк безопасной разработки ПО

NIST SSDF — это фреймворк практик безопасной разработки ПО:
PO (подготовьте организацию), PS (защитите ПО), PW (создайте
хорошо защищённое ПО), RV (отвечайте на уязвимости).
Дисциплина — практика; артефакт — профиль SSDF.

**Что наследует mathcoding:** идею «практика как требование».
Решение mathcoding может объявить `ssdf_practice`;
обязательство — свойство, которое должна удовлетворять
практика.

**Что добавляет mathcoding:** SSDF называет практику;
mathcoding привязывает практику к верификатору. Практика,
соответствующая SSDF, без верификатора — это описание;
решение mathcoding, которое называет практику и объявляет
верификатор, — это проверка. SSDF — профиль; mathcoding —
шлюз, который читает профиль.

**От чего отказывается mathcoding:** от предположения, что
профиль — это верификация. Профиль — это описание;
верификация — поизменёнческая. mathcoding заменяет профиль
поизменёнческими обязательствами.

## Что mathcoding наследует и что добавляет

mathcoding — не чистый разрыв с предыдущей работой. Это
сочетание кусков, которые уже существуют, ужесточённое тремя
свойствами, которые никакая методология не сочетает:

| Из методологии | Что наследует mathcoding |
|---|---|
| TDD | Тесты как свидетельство |
| BDD | Поведение как проверяемое заявление |
| DDD | Язык предметной области как свойство |
| FDD | Фича как единица планирования |
| MDD/MDA | Модель как артефакт первого класса |
| Spec-Driven Development | Спецификация как источник истины |
| ADR / MADR | Решение как версионированный артефакт |
| arc42 | Раздел как пространство имён |
| C4 Model | Уровень приближения как свойство |
| Living Documentation | Сгенерированный артефакт как свидетельство |
| Specification by Example | Пример как свидетель |
| OpenAPI | Машиночитаемый контракт |
| Design by Contract | Пре-/постусловие как свойство |
| Formal Methods | Доказательство как свидетельство |
| TOGAF | Фаза как свойство |
| ISO/IEC/IEEE 42010 | Интерес как свойство |
| Team Topologies | Когнитивная нагрузка как драйвер трения |
| SAFe | Каденция как свойство |
| OWASP SAMM | Функция обеспечения как свойство |
| NIST SSDF | Практика как требование |

| Что добавляет mathcoding и не предлагает ни одна из них вместе |
|---|
| Ограниченное свидетельство (субъект, обязательство, входы, среда, дайджест, метод, время) |
| Честная неопределённость (отсутствие = Inconclusive, никогда Pass) |
| Дисциплина классов источников (declared ≠ derived ≠ attested ≠ reviewed ≠ observed) |
| Дисциплина состояний вердикта (Pass ≠ Fail ≠ Inconclusive ≠ InfrastructureError) |
| Пять полос риска × четыре уровня трения |
| Требование контрпримера (для каждого неминимального решения) |
| Конечный автомат waiver'а (Active, Grace, Expired, Revoked) |
| Чек-лист перехода защищённой политики (7 стражей) |
| Само-применение (ядро проверяет собственное обновление) |
| Дайджест подложки (решения и аттестации равны по дайджесту тогда и только тогда, когда равны) |

## От чего mathcoding отказывается

Отказы mathcoding — не особенности; это граница, которая
удерживает протокол честным:

- «Утверждено» без наблюдения. Утверждение — аттестация
  `Review`; наблюдение — аттестация `Observed`; два — не
  взаимозаменяемы.
- Waiver без `expires_at`. Waiver, который не истекает, —
  это разрешение, а не отсрочка.
- `Pass` по отсутствию. Обязательство без аттестации —
  `Inconclusive`, а не `Pass`. «Я не проверял» — не «я
  проверил, и оно работает».
- Переход защищённой политики без санкционирования прежней
  политикой. Кандидат-политика не может санкционировать
  собственное принятие.
- Изменение, которое затрагивает `axioms/`, `constitution`
  или `kernel`, без контрпримера, пары фикстур и пути
  миграции.
- Решение без `risk.owner`. Владелец — это человек,
  ответственный, когда обязательство нарушается; без
  владельца решение безответственно.
- Средство исправления, названное `unassigned`, `TBD`,
  `auto` или `system`. Синтетическое средство исправления —
  это заглушка, а не средство.

## Когда mathcoding применим

Огибающая применимости (`spec/kernel-contract.md` §28) была
записана в недружественном ключе: какие проекты *не могут*
позволить себе дисциплину. Более дружественное чтение
задаёт обратный вопрос: какие проекты *выигрывают* от неё и
сколько дисциплина реально стоит?

Честный ответ таков: дисциплина дешёвая. Написать блок
`commitment:` и `obligation:` до изменения — секунды, не
часы. Вердикт ядра на проходящем изменении — субсекунды.
Стоимость mathcoding состоит из *ясности мысли*, а не из
*церемонии процесса* — а ясность мысли окупается в любом
проекте, включая самый маленький.

Успех маленького проекта обычно решается в первый час:
чем лучше вопрос, тем лучше код. Дисциплина mathcoding — в
своей основе — это дисциплина записи вопроса до кода. Это
полезно одному разработчику на хакатоне, и это полезно
пятидесяти разработчикам на регулируемой аэрокосмической
системе.

Там, где дисциплина окупается больше всего, её стоимость
невидима:

| Сигнал | Почему mathcoding помогает |
|---|---|
| Один разработчик, без аудита, срок жизни 1 год | Заставляет сформулировать вопрос до кода; стоит секунды на изменение |
| Хакатон, MVP, прототип | Заставляет назвать, что прототип должен доказать; предотвращает over-engineering по имени |
| Команда из 1 человека с ИИ-агентом кодинга | Заставляет объявить контракт до того, как агент пишет код; превращает «vibe coding» в «spec coding» |
| Два или более ИИ-агентов редактируют один репозиторий | Каждый агент обязан объявить своё обязательство; предотвращает тихую перезапись |
| Срок жизни 5+ лет, команда 3+ человека | Архитектурные решения переживают авторов; запись — план спасения |
| Требование регуляторного или контрактного аудита | Хранилище аттестаций и блокирующий шлюз — это и есть аудит |

Единственные случаи, где mathcoding — действительно
накладный расход, — это те, что ядро уже покрывает
молча: 30-секундная правка опечатки в комментарии (режим
`tiny`; ядро молчит; дисциплина невидима), однострочный
патч фикстуры (режим `light`; однострочный блок
`commitment:`), аварийное срочное исправление на продуктовом сбое
(используйте путь waiver'а; постфактум-решение обязательно
в течение 24 часов).

Во всех остальных случаях — включая «я один, и я завтра
это выброшу» — дисциплина записи вопроса до кода стоит тех
секунд, которые она занимает.

Честная ссылка по стоимости:
`mathc time-estimate --class single-file-edit --count 1 --percentile p50`
— около 3 минут полного настенного времени на решение в
одном файле. Большая часть этого времени — *мышление*, а
не *печатание*; дисциплина делает мышление явным, и в этом
её смысл.

# FAQ

> **常见问题。** 协议很小，问题却不少。

### 什么是 math-coding？

一门在实现代码之**前**，以数据包形式记录架构承诺的纪律。
内核（`mathc`）在每次合并时核对承诺与代码是否一致。

### 什么是 mathcoding？

内核所实现的方法论。Math-coding 是内核；mathcoding
是这门纪律。

### 为什么是八条原则，而不是一条？

这八条是闭合引导回路的**最小集合**。从首个提交
（`v3-alpha-0.0.1`）到内核能够检查自身的时刻（提交
`8fa7fcf`），每一项变更都必须获得这八条的同时通过。
去掉任何一条，回路都无法闭合。

### 为什么不引入真正的 YAML 库？

内核必须保持离线、且无副作用（参见
`OCAML_BEST_PRACTICES.md` §1.3、§7.3）。新增解析器依赖
会破坏内核所依托的可复现性保证。手写的子集加载器足以
处理引导阶段的文件，并且保持极小。

### 为什么 `mathc render` 使用手写的 Markdown 子集？

出于同样的原因。已发布的散文仅使用一个狭窄子集（标题、
段落、列表、代码块、边注、表格、引用）。两百行的解析器
是可审计的。引入完整的 Markdown 库会带入传递依赖，并
破坏闭包。

### 为什么是 Tufte 风格？

三个理由。(1) 留白 —— 协议本身密度很高；读者需要为
边注和参考文献留出空间。(2) 衬线字体 —— Charter /
Iowan Old Style 在长篇散文中的阅读节奏更慢，更能
维持注意力，胜过无衬线字体。(3) 克制 —— Tufte 的
配色只用一种强调色；协议的沟通模型也是如此：每段
只讲一件重要的事。

### 为什么是英文 + 俄文双语？

作者是俄国人；协议的主要受众是英语开发者社群；俄语
受众规模足够大，以至于不发布译文会造成切实的损失。
两类受众都会阅读内核输出。

### 为什么是 MathJax 而非 KaTeX？

MathJax 3 是保守之选：支持完整的 TeX/LaTeX 语法，且
对格式错误的输入较为宽容。KaTeX 更快，但只覆盖一个
较窄的子集。协议散文不需要速度。

### 为什么选 GitHub Pages？

静态 + 免费 + 已有的部署流水线
（`.github/workflows/site.yml` 已固定到 `ubuntu-22.04`）。
站点是自给自足的：描述它的同一个内核也负责生成它。

### 我可以自托管部署吗？

可以。`dist/` 目录是可移植的；用任何静态主机（nginx、
Caddy、GitHub Pages、Netlify、Vercel、Cloudflare Pages）
托管即可。通过 `--site-base ""`（相对根目录）或
`--site-base /my-app/` 覆盖 `<base href>`，以匹配部署
路径。

### 如果我不同意某条公理怎么办？

提交一个 issue。公理由「自应用」原则推导而来：规则不
约束自身的系统是不可信的。修订一项公理是一项**受保护
的策略变更**，需要在既有策略下形成决策、最强反例、
正反两面固定样本、迁移路径、恢复路径、既有策略的
授权以及一份判定变更表。参见 `AGENTS.md`
§「Self-application」。

### 从哪里入手？

1. 阅读 [Methodology](methodology.html)。
2. 阅读 [Axioms](axioms.html)。
3. 阅读 [Foundations](foundations.html)。
4. 在本仓库上运行 `mathc self-check`。
5. 将这门纪律引入你自己的项目。

# Порядок работы

> **От намерения до ревизии.** Порядок math-coding — это
> конечный автомат, описанный в `decisions/decision.yaml`,
> применяемый как дисциплина. Шесть шагов, один исполняемый
> файл.

![Конечный автомат жизненного цикла одной записи math-coding: 7 состояний (черновик, зафиксировано, реализовано, аттестовано, наблюдается, оспорено, выведено), 6 основных переходов, 4 блокирующих маркера (нарушение, отсрочка, устаревание, истечение освобождения).](assets/lifecycle-fsm.svg)

Приведённая выше диаграмма и есть порядок работы. Каждый
из шести шагов ниже соответствует одному переходу в
автомате: intent → commit → implement → attest → gate →
self_verify → merge в main. Блокирующие маркеры (нарушение,
отсрочка, устаревание, истечение освобождения) — это четыре
условия, которые могут прервать состояние и принудить
переход к более раннему.

## 1. Сформулируйте намерение

Откройте `decisions/<идентификатор>.yaml` с полем `intent:`.
Намерение — это «почему»; «что именно обещаем» приходит
следом. Запись без намерения — запись о пустоте.

```yaml
intent: |
  Добавить структурированный лог вердиктов пар
  «решение — обязательство», чтобы рецензенты могли
  ответить «безопасно ли сливать?» без перечитывания ядра.
```

## 2. Зафиксируйте обязательство

Обязательство — **фальсифицируемое утверждение**. Блок
`obligation` называет верификацию:

```yaml
commitment: |
  mathc packages --format=html собирает HTML-сетку пар
  «решение — обязательство» с вердиктами.
obligation:
  - id: packages-kernel-walker
    acceptance:
      all:
        - verifier: mathc packages --format=json
          result: pass
```

Переход от `commit` к `implement` контролируется правилом
«у каждого обязательства есть положительная и отрицательная
фикстура». Приведённое выше обязательство имеет
положительное условие приёмки
(`verifier: mathc packages --format=json, result: pass`);
соответствующее отрицательное условие (тест с
`result: fail`, который подтверждает, что верификатор
отвергает искажённое решение) добавляется на шаге 4
(Аттестация), прежде чем становится достижим переход
`implement → attest`.

## 3. Реализуйте

`lib/packages.ml` и `bin/Mathc.ml` меняются, чтобы
выполнить обязательство. Реализация остаётся на OCaml,
без побочных эффектов, около семисот строк плюс
исполняемый файл.

## 4. Аттестуйте

Запустите `scripts/generate-attestations.py` после каждой
реализации. Скрипт создаёт `attestations/<отпечаток>.json`
для каждой пары. Закоммитьте файлы аттестаций.

## 5. Проверьте шлюз

`mathc gate BASE HEAD` запускается против заполненного
хранилища. Код выхода: `0` для «успех», `1` для «блок»,
`3` для «неизвестно». Блокирующий шаг в сборочном конвейере —
`mathc self-check`.

## 6. Самопроверка

`mathc self-check` запускается против **всего** графа решений.
Код выхода открывает или блокирует слияние в `main`.
`self-check` возвращает JSON с полями `verdict`,
`subjects_count`, `pass_count` и `kernel_digest` (SHA-256
исполняемого файла, который произвёл вердикт).

![Шкала начальной загрузки: от v3-alpha-0.0.1 к 8fa7fcf (v3.0.0.19) и далее к сегодняшнему дню. Ручной режим завершается на 8fa7fcf; автоматический режим начинается с того же коммита.](assets/bootstrap-timeline.svg)

Приведённая выше шкала начальной загрузки показывает тот же
порядок работы, применённый к самому проекту. От
`v3-alpha-0.0.1` до коммита `8fa7fcf` каждый переход
допускался человеком-рецензентом (ручной режим); с
`8fa7fcf` допускающим становится ядро. Граница между
двумя режимами — шаг `mathc self-check` в этом порядке
работы.

## Развёрнутый пример

Решение о добавлении `mathc packages` прошло шесть шагов в
коммите `5d1046a`:

| Шаг | Коммит | Верификатор |
|-----|--------|-------------|
| 1. Сформулировать намерение | `mathc-packages-subcommand@1` | блок `intent:` |
| 2. Зафиксировать обязательство | тот же | `commitment:` + `obligation:` |
| 3. Реализовать | `lib/packages.ml`, `bin/Mathc.ml` | `dune build` с кодом выхода 0 |
| 4. Аттестовать | `attestations/mathc-packages-subcommand-*.json` | `mathc packages --format=json` |
| 5. Шлюз | `tests/cli/gate-{pass,fail,stale}.t` | cram-фикстуры зелёные |
| 6. Самопроверка | `tests/cli/self-check-pass.t` | cram-фикстура зелёная |

Шестиступенчатая петля — это ядро, применяющее аксиому A3
к себе. Формальное утверждение — в [Axioms](axioms.html).
